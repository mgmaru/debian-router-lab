# conntrack（コネクショントラッキング）

## conntrack とは

conntrack（connection tracking、コネクショントラッキング）は、**Linux カーネルが、自分を通る通信を1つずつ覚えておく仕組み**です。覚えた内容は、カーネルの中の **conntrack の表**に記録されます。

| 使うもの | conntrack の記録をどう使うか |
|---|---|
| NAT | 帰りの返事が届いたときに、どの通信の返事かを見つけ、宛先を書き戻す（labs/04） |
| ファイアウォール | 「すでに始まっている通信の返事は通す」（`ct state established,related accept`）を判断する（labs/05） |

conntrack はカーネルの機能なので、コマンドを何も入れなくても動いています。labs/04 で Client VM の ping の返事が書き戻されたのは、カーネルの conntrack が記録を使ったからです。記録を**見る**には、`conntrack` コマンドを使います（[docs/tools/conntrack.md](../../tools/conntrack.md)）。

---

## いつ動き始めるか

今の Linux では、conntrack は**必要になるまで関所（フック）に登録されません**。labs/04 で `sudo nft list hooks` を使って確かめました。

| 時点 | `list hooks` に conntrack が出たか |
|---|---|
| nftables のルールが何も無いとき | 出ない |
| NAT の chain を作ったとき | 出ない（`nf_nat` だけが出た） |
| `masquerade` の rule を入れたとき | **出た**（`masquerade` は、帰りの書き戻しに記録が必要だから） |

登録された処理：

| 処理 | 関所 | priority | 役割 |
|---|---|---|---|
| `ipv4_conntrack_defrag` | prerouting、output | -400 | 分割されて届いたパケットを組み立て直す。ポート番号などを読めるようにするため |
| `ipv4_conntrack_in` | prerouting | -200 | 届いたパケットが、記録済みの通信のものかを調べる。新しい通信なら、行を作り始める |
| `ipv4_conntrack_local` | output | -200 | 同じことを、Router VM 自身が送るパケットに対して行う |
| `nf_confirm` | input、postrouting | +2147483647（最大） | いちばん最後に、新しい行を確定する。途中で捨てられたパケットの行は残さない |

## 記録の1行は「2つの向き」でできている

conntrack の表は、**1つの通信につき1行**です。その1行に、通信の2つの向きが書かれています。

```text
         前半（行きの向き）                         後半（帰りの向き）
 src=10.0.0.10 dst=8.8.8.8 id=13      src=8.8.8.8 dst=192.168.22.129 id=13
 └ Client が送ったときのまま（書き換える前）┘  └ 返事が Router VM に届くときの形 ┘
```

| | 中身 | 何のためにあるか |
|---|---|---|
| 前半（行きの向き） | 行きのパケットの、**書き換える前**の形 | 返事を**どこへ戻すか**を知るため |
| 後半（帰りの向き） | 返事が Router VM に**届くときの形** | 届いたパケットが**どの通信の返事か**を見つけるため |

1行に記録しているもの：

| 記録していること | 例 |
|---|---|
| 行きの送信元・宛先 | `10.0.0.10` → `8.8.8.8` |
| 帰りに届くはずの送信元・宛先（NAT の書き換え後） | `8.8.8.8` → `192.168.22.129` |
| プロトコルと番号 | ICMP の id、TCP/UDP のポート番号 |
| 状態 | 通信が始まったばかりか、やりとりが続いているか |
| 残り時間 | この秒数のあいだ通信が無ければ、行を消す（ICMP は約30秒） |

## 1行ができるまで：conntrack が作り、NAT が後半を書き換える

行が「conntrack が書いた行」と「NAT が書いた行」の2種類あるわけではありません。**1つの通信につき1行で、その1行の後半を NAT が書き換えます。**

Client VM が ping の最初のパケットを送ったとき：

```text
 ① conntrack（prerouting、-200）が、新しい行を作る
    前半：src=10.0.0.10 dst=8.8.8.8
    後半：src=8.8.8.8  dst=10.0.0.10        ← 前半をそのまま逆にしたもの（仮の形）

 ② NAT（postrouting、+100）が、masquerade の rule に当てはまったので、
    同じ行の「後半」を書き換える
    前半：src=10.0.0.10 dst=8.8.8.8        ← そのまま
    後半：src=8.8.8.8  dst=192.168.22.129   ← 書き換えた後に返事が届く形に直す

 ③ nf_confirm（postrouting、最後）が、この行を確定する
```

| 役割 | 誰がやるか |
|---|---|
| 行を**作る** | conntrack |
| 行の後半を**書き換える** | NAT |
| 行を**確定する** | conntrack（`nf_confirm`） |

**NAT 専用の表は無い**：NAT で書き換えた結果は、conntrack の行の後半に書き込まれます。1つの記録を、conntrack と NAT が一緒に使っています。

### NAT をしない通信の行

NAT の rule に当てはまらない通信でも、conntrack は行を作ります。NAT は何も書き換えないので、後半は前半をそのまま逆にした形のままです。

| 通信 | 前半（行き） | 後半（帰り） | NAT が書き換えたか |
|---|---|---|---|
| Client VM → 8.8.8.8 の ping | `src=10.0.0.10 dst=8.8.8.8` | `src=8.8.8.8 dst=192.168.22.129` | **書き換えた**（前半を逆にした形と違う） |
| Mac → Router VM の SSH | `src=<Mac 側の IP> dst=192.168.22.129` | `src=192.168.22.129 dst=<Mac 側の IP>` | 書き換えていない（前半をそのまま逆にした形） |

**見分け方**：1行の後半が、前半をそのまま逆にした形と違っていれば、その通信は NAT されています。

## 返事が届いたとき：後半で見つけて、前半で戻す

```text
 ens33 に返事が届く： src=8.8.8.8  dst=192.168.22.129  id=13
        │
        ▼
 ① conntrack（prerouting、-200）
    届いたパケットの形を、各行の「後半」と比べて探す
    → 「src=8.8.8.8 dst=192.168.22.129 id=13」の行が見つかった
    → この行の「帰りの向き」のパケットだとわかる
        │
        ▼
 ② nf_nat（prerouting、-100）
    同じ行の「前半」を見る
    → 行きの送信元は 10.0.0.10 だった
    → 宛先 IP を 10.0.0.10 に書き戻す
        │
        ▼
 ③ ルーティング判断
    宛先が 10.0.0.10 → 10.0.0.0/24 dev ens37 の行 → ens37 から送り出す
```

- **後半で「見つける」**：届いた返事の形（`dst=192.168.22.129`）は、後半とぴったり同じ。そのため、後半と比べればどの行かがわかる
- **前半で「戻す先を知る」**：書き戻す先の `10.0.0.10` は、前半にしか書かれていない
- **conntrack（-200）が NAT（-100）より先**：先に行を見つけないと、NAT は書き戻す先がわからない
- **全部がルーティング判断より前**：書き戻した宛先 `10.0.0.10` で、ens37 への経路が選ばれる

### 書き換えるのは「宛先 IP の欄」、送り先を決めるのはルーティング

| 処理 | やること |
|---|---|
| NAT（②） | 宛先 IP を `192.168.22.129` から `10.0.0.10`（1台の住所）に書き換える |
| ルーティング（③） | 宛先 `10.0.0.10` を見て、ens37（ローカルネットワーク側）から出すと決める |

NAT が「ローカルネットワークへ送る」のではありません。行きのときと同じで、NAT は「書き換え」、ルーティングは「どこへ渡すか」と役割が分かれています。

### なぜ id（ポート番号）も記録するのか

Client が2台あって、2台とも 8.8.8.8 へ ping を送ると、返事はどちらも `src=8.8.8.8 dst=192.168.22.129` で届きます。IP だけでは、どちらの返事か区別できません。

そこで、ICMP の id（TCP/UDP ならポート番号）も含めて比べます。id がぶつかった場合は、行きのときに NAT が id をずらして、後半が重ならないようにします（[質問63 の補足1](../../questions/2026-11-05-nat-rewrites-header-field.md)）。

## カーネルのほかの表との違い

NAT とファイアウォールが使う**通信の記録**は、conntrack の表だけです。カーネルにはほかの表もありますが、用途が違います。

| 表 | 記録しているもの | 見るコマンド | NAT に使うか |
|---|---|---|---|
| **conntrack の表** | Router VM を**通る**通信 | `conntrack -L` | **使う** |
| ルーティングテーブル | 宛先ごとの渡す相手 | `ip route` | 使わない（書き戻した後の行き先を決める） |
| 近隣テーブル | IP と MAC の対応 | `ip neigh` | 使わない（次の1台の MAC を引く） |
| ソケットの表 | Router VM **自身が**送受信している通信（SSH など） | `ss` | 使わない |

### conntrack の表とソケットの表

どちらも「通信の記録」ですが、**誰の通信か**が違います。

| | conntrack の表 | ソケットの表（`ss`） |
|---|---|---|
| 記録する通信 | Router VM を通るものすべて（転送も、自分宛ても） | Router VM 自身のプログラムが使っている通信だけ |
| Client VM から 8.8.8.8 への ping | **載る** | **載らない**（Router VM のプログラムは関わっていない） |
| Mac から Router VM への SSH | 載る | 載る |

転送するパケットは、カーネル空間の中だけで処理されます（[Linux カーネルの「カーネル空間とユーザー空間」](README.md#カーネル空間とユーザー空間)）。そのため、Router VM 自身のプログラムの通信を記録するソケットの表には出てきません。転送する通信を覚えているのは、conntrack の表だけです。

## 記録を見るツール

記録そのものはカーネルに1つしかありません。どのツールも、同じ conntrack の表を見る（または写す）ものです。

| 方法 | 説明 |
|---|---|
| `conntrack` コマンド | いちばん一般的（[docs/tools/conntrack.md](../../tools/conntrack.md)） |
| `/proc/net/nf_conntrack` | 記録をファイルの形で読める。ただし Debian では、カーネルの設定によって**このファイルが無い**ことがある |
| `conntrackd` | 2台のルーターの間で、記録を同期するプログラム。1台が故障したときに、もう1台が通信を引き継げるようにする |

`conntrack` コマンドと表の関係は、`ip route` とルーティングテーブル、`nft` と nftables のルールの関係と同じです。表はカーネルの中にあり、コマンドはユーザー空間から Netlink で「中身を見せて」「この行を消して」と頼むだけです。
