# パケットの処理の流れ

パケットが NIC に届いてから出ていくまでに、Linux カーネルの中でどんな処理を、どの順番で通るかをまとめます。

関所（Netfilter のフック）は、この流れの途中にある「呼び出し口」です。関所そのものの説明は [関所（Netfilter のフック）](netfilter-hooks.md) にあります。このドキュメントは、**関所と関所の間で、カーネルが何をしているか**を扱います。

---

## 全体の流れ（転送するパケット）

Client VM から 8.8.8.8 への ping が、Router VM を通り抜けるときの流れです。

```text
 ens37 にパケットが届く
   │
   ├─ 1. NIC ドライバー     パケットを受け取り、sk_buff（パケットの入れ物）を作る。届いた NIC を記録する
   ├─ 2. Ethernet の処理    宛先 MAC アドレスを見る。中身が IPv4 か IPv6 かを判断する
   ├─ 3. IP の受信処理      IP ヘッダーが正しい形か確かめる。TCP・UDP・ICMP のヘッダーの位置を記録する
   │
   ├─ ① prerouting        組み立て直し → conntrack（new か established か）→ NAT の宛先の書き戻し
   │
   ├─ 4. ルーティング判断   自分宛てか転送かを決める。転送なら ip_forward を確かめ、出口の NIC と次の機器を決める
   ├─ 5. 転送の処理         TTL を 1 減らす（1 だったら捨てて、Time Exceeded を返す）
   │
   ├─ ③ forward           ファイアウォール（labs/05）
   ├─ ⑤ postrouting       NAT の送信元の書き換え（マスカレード）→ conntrack の記録を確定する
   │
   ├─ 6. 近隣テーブル       次の機器（192.168.22.2）の MAC アドレスを引く。知らなければ ARP で問い合わせる
   └─ 7. NIC ドライバー     Ethernet ヘッダーを付けて、ens33 から送り出す
```

番号の付いた段（1〜7）はカーネルの処理、丸数字（①③⑤）は関所です。関所に置いた rule は、**その前の段までに記録されたこと**を使って条件を調べます。

---

## sk_buff：パケットと「下調べの結果」を入れる箱

カーネルの中では、パケットは **sk_buff**（ソケットバッファ、略して skb）という入れ物に入れて運ばれます。sk_buff には、パケットのデータそのものに加えて、**各段が調べた結果**が書き込まれていきます。

```text
 sk_buff
 ├─ パケットのデータ（Ethernet・IP・ICMP のヘッダーと中身）
 │
 └─ 下調べの結果
     ├─ 届いた NIC                   ← 1. NIC ドライバーが書く
     ├─ IPv4 か IPv6 か              ← 2. Ethernet の処理が書く
     ├─ IP ヘッダーの位置             ← 2. Ethernet の処理が書く
     ├─ TCP/UDP ヘッダーの位置        ← 3. IP の受信処理が書く
     ├─ conntrack の記録と状態        ← ① prerouting の conntrack が書く
     └─ 経路（出口の NIC・次の機器）   ← 4. ルーティング判断が書く
```

| sk_buff に書かれること | 書く段 | 使う rule の条件（nftables） | カーネルの中の名前（参考） |
|---|---|---|---|
| 届いた NIC | 1. NIC ドライバー | `iifname` | `skb->dev` |
| IPv4 か IPv6 か | 2. Ethernet の処理 | `meta nfproto`（`inet` の table で使う） | `skb->protocol` |
| IP ヘッダーの位置 | 2. Ethernet の処理 | `ip saddr`、`ip daddr` など | `skb->network_header` |
| TCP/UDP ヘッダーの位置 | 3. IP の受信処理 | `tcp dport`、`udp dport` など | `skb->transport_header` |
| conntrack の記録と状態 | ① prerouting | `ct state` | `skb->_nfct` |
| 経路（出口の NIC・次の機器） | 4. ルーティング判断 | `oifname` | `skb_dst(skb)` |

rule は、sk_buff に書かれた**位置**を使って、パケットのデータから必要な欄を読みます。たとえば `tcp dport 22` は「TCP ヘッダーの位置から 2 バイト目の 2 バイト」を読みます（[firewall.md の「下調べと、rule が読む欄の分担」](../firewall.md#下調べとrule-が読む欄の分担)）。

## 各段で何をするか

### 1. NIC ドライバー（受信）

| すること | 説明 |
|---|---|
| パケットを受け取る | NIC が受け取った Ethernet フレームを、メモリに取り込む |
| sk_buff を作る | パケットを入れ物に入れる。ここから先は、すべて sk_buff を受け渡して処理する |
| 届いた NIC を記録する | `ens37` など。`tcpdump -i ens37` で見えるのは、このあたりのパケット |

### 2. Ethernet の処理

| すること | 説明 |
|---|---|
| 宛先 MAC アドレスを見る | 自分の MAC アドレス宛てか、ブロードキャストか、ほかの機器宛てかを記録する。ほかの機器宛ては、IP の受信処理で捨てられる |
| 中身の種類を判断する | Ethernet ヘッダーの「種類」の欄（`0x0800` なら IPv4、`0x86dd` なら IPv6、`0x0806` なら ARP）を見て、次に渡す処理を決める |

### 3. IP の受信処理

| すること | 説明 |
|---|---|
| IP ヘッダーを確かめる | バージョン、ヘッダーの長さ、全体の長さ、チェックサムが正しいか。おかしければ**ここで捨てる** |
| TCP/UDP ヘッダーの位置を記録する | IP ヘッダーの長さの欄から、その後ろのヘッダーがどこから始まるかを計算して記録する |
| ① prerouting を呼ぶ | 関所に登録されたもの（conntrack、NAT、自分の chain）を順に呼ぶ |

### ① prerouting

| priority | 処理 | すること |
|---|---|---|
| -400 | 組み立て直し（defrag） | 分割されて届いたパケットを1つに戻す。conntrack がポート番号を読めるようにするため |
| -200 | conntrack | 表を引き、`new`・`established` などを決めて sk_buff に記録する |
| -100 | NAT | NAT の返事なら、宛先を書き戻す（192.168.22.129 → 10.0.0.10） |

詳しくは [nftables.md の「関所の名前を確かめる方法」](nftables.md#関所の名前を確かめる方法) と [conntrack.md](conntrack.md) にあります。

### 4. ルーティング判断

| すること | 説明 |
|---|---|
| 自分宛てか転送かを決める | 宛先が Router VM 自身の IP なら「自分宛て」→ ② input へ。そうでなければ「転送」 |
| 転送してよいか確かめる | `net.ipv4.ip_forward` が 0 なら、転送せずに捨てる |
| 出口と次の機器を決める | ルーティングテーブルをロンゲストマッチで引く。8.8.8.8 なら default の行 → 出口 `ens33`、次の機器 `192.168.22.2` |

① prerouting で宛先が書き戻されたあとなので、NAT の返事は `10.0.0.10` 宛てとしてルーティングされ、出口が `ens37` になります。

### 5. 転送の処理

| すること | 説明 |
|---|---|
| TTL を確かめて、1 減らす | TTL が 1 なら、これ以上転送できないので捨て、送り主に ICMP の Time Exceeded を返す。そうでなければ 1 減らす |
| ③ forward を呼ぶ | ファイアウォールの chain が、ここで通すか捨てるかを決める |

TTL を減らすのは ③ forward より**前**です。そのため ③ forward の rule が見る TTL は、すでに 1 減った値です。

### ⑤ postrouting

| priority | 処理 | すること |
|---|---|---|
| 100 | NAT | 新しい通信なら、nat の chain（`masquerade`）を呼んで送信元を書き換える。2つ目以降のパケットは、conntrack の記録どおりに書き換える |
| 最大 | conntrack の確定（`nf_confirm`） | 新しい通信の記録を、表に正式に載せる。途中の関所で捨てられたパケットの記録は、ここまで来ないので残らない |

### 6. 近隣テーブル

| すること | 説明 |
|---|---|
| 次の機器の MAC アドレスを引く | ルーティング判断で決めた次の機器（192.168.22.2）の MAC アドレスを、近隣テーブル（`ip neigh`）から探す |
| 知らなければ ARP で問い合わせる | 返事が来るまで、パケットは待たされる |
| Ethernet ヘッダーを付ける | 宛先 MAC = 次の機器、送信元 MAC = 出口の NIC（[neighbor.md](../neighbor.md)） |

### 7. NIC ドライバー（送信）

出口の NIC（`ens33`）から送り出します。`tcpdump -i ens33` で見えるのは、NAT で書き換えた**後**のパケットです。

## ほかの2つの道

### Router VM に届くパケット（Mac → Router VM への SSH）

```text
 ens33 に届く → 1〜3 → ① prerouting → 4. ルーティング判断（自分宛て）→ ② input
   → conntrack の記録を確定する → TCP の処理 → sshd が受け取る
```

- 5. 転送の処理は通らないので、TTL は減らない
- ② input のあと、TCP の処理がポート番号を見て、そのポートで待っているプログラム（ソケット）に渡す。待っているプログラムがいなければ、TCP の RST を返す

### Router VM から出るパケット（`apt update`、SSH の返事）

```text
 プログラムがデータを送る → TCP/UDP の処理 → 4. ルーティング判断（出口を決める）
   → ④ output → ⑤ postrouting → 6. 近隣テーブル → 7. NIC ドライバー
```

- プログラムが作ったパケットなので、1〜3 と ① prerouting は通らない
- ルーティング判断は ④ output より**前**にある。④ output の rule がパケットを書き換えたときだけ、ルーティングをやり直す

---

## 関所に来る前に捨てられるパケット

次のパケットは、関所に届く前にカーネルが捨てます。**nftables の rule には一度も来ない**ので、`counter` にも数えられません。

| 捨てられるパケット | 捨てる段 |
|---|---|
| ほかの機器の MAC アドレス宛て | 3. IP の受信処理 |
| IP ヘッダーが壊れている（長さやチェックサムがおかしい） | 3. IP の受信処理 |

一方、次のパケットは ① prerouting を通ったあとで捨てられます。

| 捨てられるパケット | 捨てる段 |
|---|---|
| 転送が必要だが `ip_forward` が 0 | 4. ルーティング判断 |
| ルーティングテーブルに当てはまる行が無い | 4. ルーティング判断 |
| TTL が 1 で、これ以上転送できない | 5. 転送の処理 |

「rule を入れていないのに通らない」ときは、これらの段で捨てられていないかを疑います。
