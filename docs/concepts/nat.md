# NAT

## NAT とは

NAT（Network Address Translation）は、**ルーターがパケットを転送するときに、IP アドレスを書き換える仕組み**です。

このラボで使うのは、**送信元 IP を書き換える NAT**（Source NAT、SNAT）です。Linux では、出ていく NIC の IP に自動で書き換える SNAT を**マスカレード**と呼びます。

NAT の本質は、次の一文にまとまります。

> **外側が知らない送信元のまま出すと、返事は戻ってこない。だから、出ていくときに「返事が戻ってこられる送信元」に書き換える。**

NAT は、戻ってきた返事を受け取れるようにする設定ではありません。**出ていくときに書き換える**設定です。

---

## このラボの経路

```text
 [Client VM]            [Router VM]                [VMware NAT]
 10.0.0.10   ──→  ens37 ─────── ens33   ──→  192.168.22.2  ──→  Windows  ──→  家のルーター  ──→  インターネット  ──→  8.8.8.8
                  10.0.0.1      192.168.22.129
 └──── 10.0.0.0/24 ────┘        └──── 192.168.22.0/24 ────┘
   Router VM の内側（LAN）            Router VM の外側（WAN）
```

| ネットワーク | 知っている機器 |
|---|---|
| `10.0.0.0/24` | Client VM と Router VM だけ。ラボで勝手に作ったネットワークなので、VMware NAT から先は知らない |
| `192.168.22.0/24` | Router VM と VMware NAT。VMware が用意したネットワークなので、VMware NAT は知っている |

## NAT が無いとき：返事が戻ってこない

### 確かめた結果（2026-11-05）

Client VM から `ping 8.8.8.8` を送り、Router VM の両側の NIC で `tcpdump` を取りました。

ens37（LAN 側）：

```text
kajih@debian-router:~$ sudo tcpdump -n -i ens37 icmp
00:20:23.334156 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 10, seq 1, length 64
00:20:24.360163 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 10, seq 2, length 64
00:20:25.383640 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 10, seq 3, length 64
```

ens33（WAN 側）：

```text
kajih@debian-router:~$ sudo tcpdump -n -i ens33 icmp
00:23:19.461296 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 12, seq 1, length 64
00:23:20.486323 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 12, seq 2, length 64
00:23:21.510702 IP 10.0.0.10 > 8.8.8.8: ICMP echo request, id 12, seq 3, length 64
```

- どちらの NIC にも echo request だけが出ていて、**echo reply は1つも出ていない**
- ens33 から出ていくパケットの送信元は、**`10.0.0.10` のまま**。Router VM は転送しているだけで、書き換えていない

### 何が起きているか

```text
 Client VM        Router VM               VMware NAT から先
 10.0.0.10  ──→  ens37 → ens33  ──→  ✕  「10.0.0.10 って誰？」
                  （転送はできている）       （ここから先で無くなる）

 src 10.0.0.10    src 10.0.0.10（そのまま）
 dst 8.8.8.8      dst 8.8.8.8
```

1. Client VM が `src 10.0.0.10 → dst 8.8.8.8` の ping を、デフォルトゲートウェイ `10.0.0.1`（Router VM）へ渡す
2. Router VM は、IP フォワードが ON なので転送する。ルーティングテーブルの `default via 192.168.22.2 dev ens33` に従い、ens33 から `192.168.22.2` へ渡す
3. 送信元は `10.0.0.10` のまま。**Router VM より外側**で、パケットか返事が無くなる

外側で無くなる理由は、次のどちらかです。

- **途中で捨てられる**：VMware NAT などが、知らないネットワーク（`10.0.0.0/24`）からのパケットを外へ出さない
- **返事が戻れない**：仮に 8.8.8.8 まで届いても、`10.0.0.10` はプライベートアドレス。世界中の家庭や会社で同じアドレスが使われているので、インターネット上のルーターは「どの `10.0.0.10` へ返せばよいか」がわからない。プライベートアドレス宛てのパケットは、インターネットでは運べない決まりになっている

どちらが起きているかは、Router VM の `tcpdump` だけでは区別できません。ただ、どちらの場合も「`10.0.0.10` を送信元にしたまま外へ出すと、返事は戻らない」という結論は同じです。

### よくある誤解：「返事が Router VM に届いたが、NAT が無いので捨てた」

これは違います。理由は2つあります。

1. **ens33 に reply が映っていない**：`tcpdump` は、NIC にパケットが届いた時点で表示する。Router VM が捨てる場合でも、捨てる前に表示される。返事が Router VM まで戻ってきていれば、ens33 に `8.8.8.8 > 10.0.0.10: ICMP echo reply` が出ていたはず
2. **仮に届いても、Router VM は捨てない**：ルーティングテーブルに `10.0.0.0/24 dev ens37` の行があり、IP フォワードも ON。`10.0.0.10` 宛ての返事が届けば、Client VM へ転送する

返事は Router VM まで**戻ってきていない**、というのが正しい理解です。

## NAT があるとき：返事が戻ってくる

```text
【行き】
 Client VM               Router VM                         外へ
 10.0.0.10  ──→  ens37 ─────────── ens33  ──→  192.168.22.2  ──→ … ──→  8.8.8.8
                          ①書き換える
                          ②記録する（conntrack）

 src 10.0.0.10                     src 192.168.22.129   ← 書き換わる
 dst 8.8.8.8                       dst 8.8.8.8

【帰り】
 Client VM               Router VM                         外から
 10.0.0.10  ←──  ens37 ─────────── ens33  ←──  192.168.22.2  ←── … ←──  8.8.8.8
                          ③記録を見て書き戻す

 src 8.8.8.8                       src 8.8.8.8
 dst 10.0.0.10   ← 書き戻る         dst 192.168.22.129
```

1. **書き換える（行き）**：Router VM が、送信元を `10.0.0.10` から、自分の WAN 側 IP `192.168.22.129` に書き換えて送り出す
2. **記録する**：「`10.0.0.10` の通信を `192.168.22.129` に書き換えた」ことを記録しておく。この記録を **conntrack**（コネクショントラッキング）と呼ぶ
3. **返事が戻ってくる**：外側の機器は `192.168.22.129` を知っているので、返事は Router VM まで戻ってくる
4. **書き戻す（帰り）**：Router VM は記録を見て「これは `10.0.0.10` の通信の返事だ」と判断し、宛先を `10.0.0.10` に書き戻す。ルーティングテーブルの `10.0.0.0/24 dev ens37` に従い、ens37 から Client VM へ転送する

### 書き換えるタイミング

| | タイミング | 理由 |
|---|---|---|
| 行き（送信元の書き換え） | ルーティング判断の**後**（nftables の postrouting） | 出ていく NIC が決まらないと、どの IP に書き換えるかわからない |
| 帰り（宛先の書き戻し） | ルーティング判断の**前**（nftables の prerouting の場所） | 先に宛先を `10.0.0.10` に戻さないと、Router VM 自身宛てと判断されてしまう |

自分で書く NAT のルールは、行きの1つだけ。NAT のルールが見られるのは通信の最初のパケットだけで、帰りの書き戻しと2つ目以降のパケットの書き換えは、conntrack の記録を使って自動で行われる。詳しくは [nftables はルーティングテーブルのようなものか](../questions/2026-11-05-nftables-vs-routing-table.md) を参照。

### NAT で変わるもの・変わらないもの

| | NAT なし | NAT あり |
|---|---|---|
| 渡す相手（ルーティングテーブルで決まる） | `192.168.22.2` | `192.168.22.2`（**変わらない**） |
| 出ていくパケットの送信元 IP | `10.0.0.10` | `192.168.22.129` |
| 返事 | 戻ってこない | 戻ってくる |

NAT で変わるのは**送信元 IP だけ**です。どこへ渡すかは、NAT の有無にかかわらずルーティングテーブルが決めます。

## IP フォワードと NAT の役割の違い

Client VM がインターネットと通信するには、**両方**が必要です。

| 仕組み | 役割 | このラボの状態 |
|---|---|---|
| IP フォワード | 自分宛てではないパケットを、ルーティングテーブルが示す NIC から**通す**かどうか | ON（[labs/02](../../labs/02-ip-forwarding/README.md) で有効化） |
| NAT | 通すパケットの送信元 IP を**書き換える**かどうか | まだ設定していない（[labs/04](../../labs/04-nat/README.md)） |

- IP フォワードは向きを区別しない。LAN → WAN にも、WAN → LAN にも転送する。NAT の帰りの書き戻しの後は、WAN → LAN の転送が使われる
- `ip route show default` に出る `src 192.168.22.129` は、Router VM **自身が**作ったパケットに使われる送信元。転送する Client VM のパケットには使われない。Client VM のパケットにもこの IP を使わせるのが、マスカレード

## NAT は何段も重なっている

このラボの経路では、NAT が何回も行われています。

```text
 10.0.0.10  ─[Router VM の NAT]→  192.168.22.129  ─[VMware NAT]→  Windows の IP  ─[家のルーター]→  グローバル IP  →  インターネット
```

- **VMware NAT**：`192.168.22.0/24` を、Windows の IP に書き換える
- **家のルーター**：家の LAN のアドレスを、プロバイダからもらったグローバル IP に書き換える

各段の NAT が知っているのは、**自分のすぐ内側のネットワークだけ**です。VMware NAT は `192.168.22.0/24` を知っていますが、Router VM の内側の `10.0.0.0/24` は知りません。だから Router VM 自身が、`10.0.0.0/24` を `192.168.22.129` に書き換える必要があります。

家庭用ルーターがやっていることも、これから Router VM に設定することと同じです。
