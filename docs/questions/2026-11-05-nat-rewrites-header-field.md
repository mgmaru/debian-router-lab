# NAT は送信元を取り外して付け替えるのか：パケットの図で見る、書き換わる欄とそのままの欄

調査日：2026-11-05

- [labs/03-routing](../../labs/03-routing/README.md)（転送で MAC アドレスと TTL が変わることを観察）

## 疑問

> **質問63**：NAT はパケットの送信元を書き換えるとのことだが、元のローカルネットワークの送信元のパケットを取り外して、新しい送信元のパケットを取り付けるという感じか？ パケットの図で説明してほしい。

## 結論

| 質問 | 答え |
|---|---|
| NAT は送信元を取り外して付け替える？ | **違う。** IP ヘッダーはそのまま使い、その中の**「送信元 IP」の欄だけを上書きする** |
| 「取り外して付け替える」に当たるものはある？ | **Ethernet ヘッダー（MAC アドレス）。** これは NAT ではなく転送の働きで、区間ごとに付け替えられる |
| 外側に新しいヘッダーを取り付ける仕組みはある？ | **カプセル化**（VPN などで使う）。NAT とは別の仕組み |

## パケットの構造

パケットは、データの前にいくつかの「ヘッダー」（宛名書きのようなもの）が付いた形をしている。ping のパケットはこうなっている。

```text
┌──────────────────┬───────────────────────────────┬─────────────────┬──────────┐
│ Ethernet ヘッダー │ IP ヘッダー                    │ ICMP ヘッダー    │ データ    │
│                  │                               │                 │          │
│ 宛先 MAC          │ 送信元 IP   10.0.0.10         │ type: echo req  │ 56 バイト │
│ 送信元 MAC        │ 宛先 IP     8.8.8.8           │ id: 10          │          │
│                  │ TTL         64                │ seq: 1          │          │
│                  │ チェックサム                    │                 │          │
└──────────────────┴───────────────────────────────┴─────────────────┴──────────┘
```

NAT が触るのは、この中の **IP ヘッダーの「送信元 IP」の欄**である。

## NAT の前と後（Router VM の ens37 → ens33）

```text
【ens37 に届いたとき】
┌──────────────────────────┬─────────────────────────────┬────────────┬────────┐
│ 宛先 MAC   Router の ens37 │ 送信元 IP   10.0.0.10        │ ICMP       │ データ  │
│ 送信元 MAC Client          │ 宛先 IP     8.8.8.8          │ id: 10     │        │
│                          │ TTL         64              │ seq: 1     │        │
└──────────────────────────┴─────────────────────────────┴────────────┴────────┘
            │                          │                       │           │
         付け替え                   欄を上書き               そのまま     そのまま
            ↓                          ↓                       ↓           ↓
【ens33 から出ていくとき】
┌──────────────────────────┬─────────────────────────────┬────────────┬────────┐
│ 宛先 MAC   192.168.22.2    │ 送信元 IP   192.168.22.129 ★ │ ICMP       │ データ  │
│ 送信元 MAC Router の ens33 │ 宛先 IP     8.8.8.8          │ id: 10     │        │
│                          │ TTL         63              │ seq: 1     │        │
└──────────────────────────┴─────────────────────────────┴────────────┴────────┘
                                ★ NAT で変わる
```

`宛先 MAC 192.168.22.2` は、「`192.168.22.2` の MAC アドレス」という意味。

| 部分 | 何が起きるか | 誰がやるか |
|---|---|---|
| Ethernet ヘッダー | **丸ごと取り外して、新しく付け替える** | 転送（区間ごと。labs/03 で確認済み） |
| IP ヘッダーの送信元 IP | **欄を上書きする** | NAT |
| IP ヘッダーの TTL | 1 減らす | 転送 |
| IP ヘッダーのチェックサム | 計算し直す（中身が変わったので） | 転送と NAT |
| 宛先 IP、ICMP、データ | **そのまま** | — |

「取り外して付け替える」というイメージは、Ethernet ヘッダー（MAC アドレス）には当てはまる。IP ヘッダーは付け替えずに、同じヘッダーの欄を書き換える。

帰りの返事では、逆に**宛先 IP の欄**が `192.168.22.129` から `10.0.0.10` に上書きされる（書き戻し）。

## 補足1：番号も書き換えることがある

正確には、NAT は IP だけでなく、ICMP の `id` や TCP/UDP の**ポート番号**を書き換えることもある。

Client が複数いて、たまたま同じ `id`（TCP/UDP なら同じポート番号）で外へ出ようとすると、送信元 IP はどちらも `192.168.22.129` になる。これでは帰りに「どちらの返事か」を区別できない。そういう場合に、Router VM が番号をずらして区別する。Client が1台の今のラボでは、たいてい `id` はそのまま。

TCP/UDP では、ヘッダーのチェックサムに IP アドレスも含めて計算するので、送信元 IP を書き換えると TCP/UDP のチェックサムも計算し直す。ICMP のチェックサムは IP アドレスを含まないので、`id` を書き換えない限りそのまま。

## 補足2：「取り付ける」に当たる仕組みは別にある

「元のパケットはそのままで、外側に新しいヘッダーを取り付ける」仕組みもある。これは**カプセル化**と呼ばれ、VPN などで使われる（[labs/10-vpn](../../labs/10-vpn/README.md)）。

```text
NAT：         [IP ヘッダー（送信元を上書き）][ICMP][データ]
カプセル化：  [新しい IP ヘッダー][元の IP ヘッダー][ICMP][データ]  ← 外側に足す
```

NAT は上書き、カプセル化は追加、と区別しておくと、VPN を学ぶときに混乱しにくい。

## 確かめ方（NAT を設定した後）

Router VM で、ens37 と ens33 の `tcpdump` を別のターミナルで動かしたまま、Client VM から `ping -c 3 8.8.8.8` を送る。

```bash
sudo tcpdump -n -e -v -i ens37 icmp
sudo tcpdump -n -e -v -i ens33 icmp
```

予想：

- MAC アドレス（`-e` で表示）は、両側で違う
- 送信元 IP は、ens37 では `10.0.0.10`、ens33 では `192.168.22.129`
- TTL（`-v` で表示）は、ens37 では 64、ens33 では 63
- 宛先 IP（`8.8.8.8`）と ICMP の `id`・`seq` は、両側で同じ
