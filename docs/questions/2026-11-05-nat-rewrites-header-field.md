## 疑問

> **質問63**：NAT はパケットの送信元を書き換えるとのことだが、元のローカルネットワークの送信元のパケットを取り外して、新しい送信元のパケットを取り付けるという感じか？ パケットの図で説明してほしい。

> **質問64（追加質問）**：なぜ IP ヘッダーは書き換えで、Ethernet ヘッダーは付け替えなのか？ Ethernet ヘッダーも書き換えで良いような気がする。

> **質問65（追加質問）**：MAC アドレスは、NIC に付いている番号のことか？

## 結論

| 質問 | 答え |
|---|---|
| NAT は送信元を取り外して付け替える？ | **違う。** IP ヘッダーはそのまま使い、その中の**「送信元 IP」の欄だけを上書きする** |
| 「取り外して付け替える」に当たるものはある？ | **Ethernet ヘッダー（MAC アドレス）。** これは NAT ではなく転送の働きで、区間ごとに付け替えられる |
| 外側に新しいヘッダーを取り付ける仕組みはある？ | **カプセル化**（VPN などで使う）。NAT とは別の仕組み |
| なぜ IP ヘッダーは書き換えで、Ethernet ヘッダーは付け替え？ | **有効な範囲が違うから。** Ethernet ヘッダーは1区間だけの使い捨てで、次の区間の形も中身も前の区間と無関係に決まる。IP ヘッダーは最初から最後まで使い続けるので、大部分を残して必要な欄だけ直す。ただし、両方の区間が Ethernet なら、結果は「MAC の欄を書き換えた」のと区別がつかない |
| MAC アドレスは NIC に付いている番号？ | **その通り。** NIC 1枚ごとに1つ付いている。NIC が2枚あれば MAC アドレスも2つある |

## パケットの構造

パケットは、データの前にいくつかの「ヘッダー」（宛名書きのようなもの）が付いた形をしている。ping のパケットはこうなっている。

```text
┌──────────────────┬───────────────────────────────┬─────────────────┬──────────┐
│ Ethernet ヘッダー │ IP ヘッダー                    │ ICMP ヘッダー    │ データ    │
│                  │                               │                 │          │
│ 宛先 MAC          │ 送信元 IP   10.0.0.10         │ type: echo req  │ 56 バイト │
│ 送信元 MAC        │ 宛先 IP     8.8.8.8           │ id: 10          │          │
│                  │ TTL         64                │ seq: 1          │          │
│                  │ チェックサム                    │                 │          │
└──────────────────┴───────────────────────────────┴─────────────────┴──────────┘
```

NAT が触るのは、この中の **IP ヘッダーの「送信元 IP」の欄**である。

## NAT の前と後（Router VM の ens37 → ens33）

```text
【ens37 に届いたとき】
┌──────────────────────────┬─────────────────────────────┬────────────┬────────┐
│ 宛先 MAC   Router の ens37 │ 送信元 IP   10.0.0.10        │ ICMP       │ データ  │
│ 送信元 MAC Client          │ 宛先 IP     8.8.8.8          │ id: 10     │        │
│                          │ TTL         64              │ seq: 1     │        │
└──────────────────────────┴─────────────────────────────┴────────────┴────────┘
            │                          │                       │           │
         付け替え                   欄を上書き               そのまま     そのまま
            ↓                          ↓                       ↓           ↓
【ens33 から出ていくとき】
┌──────────────────────────┬─────────────────────────────┬────────────┬────────┐
│ 宛先 MAC   192.168.22.2    │ 送信元 IP   192.168.22.129 ★ │ ICMP       │ データ  │
│ 送信元 MAC Router の ens33 │ 宛先 IP     8.8.8.8          │ id: 10     │        │
│                          │ TTL         63              │ seq: 1     │        │
└──────────────────────────┴─────────────────────────────┴────────────┴────────┘
                                ★ NAT で変わる
```

`宛先 MAC 192.168.22.2` は、「`192.168.22.2` の MAC アドレス」という意味。

| 部分 | 何が起きるか | 誰がやるか |
|---|---|---|
| Ethernet ヘッダー | **丸ごと取り外して、新しく付け替える** | 転送（区間ごと。labs/03 で確認済み） |
| IP ヘッダーの送信元 IP | **欄を上書きする** | NAT |
| IP ヘッダーの TTL | 1 減らす | 転送 |
| IP ヘッダーのチェックサム | 計算し直す（中身が変わったので） | 転送と NAT |
| 宛先 IP、ICMP、データ | **そのまま** | — |

「取り外して付け替える」というイメージは、Ethernet ヘッダー（MAC アドレス）には当てはまる。IP ヘッダーは付け替えずに、同じヘッダーの欄を書き換える。

帰りの返事では、逆に**宛先 IP の欄**が `192.168.22.129` から `10.0.0.10` に上書きされる（書き戻し）。

## 補足1：番号も書き換えることがある

正確には、NAT は IP だけでなく、ICMP の `id` や TCP/UDP の**ポート番号**を書き換えることもある。

Client が複数いて、たまたま同じ `id`（TCP/UDP なら同じポート番号）で外へ出ようとすると、送信元 IP はどちらも `192.168.22.129` になる。これでは帰りに「どちらの返事か」を区別できない。そういう場合に、Router VM が番号をずらして区別する。Client が1台の今のラボでは、たいてい `id` はそのまま。

TCP/UDP では、ヘッダーのチェックサムに IP アドレスも含めて計算するので、送信元 IP を書き換えると TCP/UDP のチェックサムも計算し直す。ICMP のチェックサムは IP アドレスを含まないので、`id` を書き換えない限りそのまま。

## 補足2：「取り付ける」に当たる仕組みは別にある

「元のパケットはそのままで、外側に新しいヘッダーを取り付ける」仕組みもある。これは**カプセル化**と呼ばれ、VPN などで使われる（[labs/10-vpn](../../labs/10-vpn/README.md)）。

```text
NAT：         [IP ヘッダー（送信元を上書き）][ICMP][データ]
カプセル化：  [新しい IP ヘッダー][元の IP ヘッダー][ICMP][データ]  ← 外側に足す
```

NAT は上書き、カプセル化は追加、と区別しておくと、VPN を学ぶときに混乱しにくい。

## 質問64：なぜ IP ヘッダーは書き換えで、Ethernet ヘッダーは付け替えなのか

### 有効な範囲が違う

```text
 Client VM ─────── Router VM ─────── 192.168.22.2 ─── … ─── 8.8.8.8
          区間1               区間2

 Ethernet ヘッダー： [区間1 用]        [区間2 用]       （区間ごとに別物）
 IP ヘッダー：      [────────── 最初から最後まで同じ 1つ ──────────]
```

| ヘッダー | 有効な範囲 | 中身の意味 |
|---|---|---|
| Ethernet ヘッダー | **1区間だけ**（同じネットワークの中） | 「この区間で、次に誰に渡すか」 |
| IP ヘッダー | **最初から最後まで** | 「最終的に誰から誰へ」 |

Ethernet ヘッダーは、Router VM に届いた時点で**役目を終える**。区間1 の「Client から Router の ens37 へ」という情報は、区間2 では何の意味もない。そのため、受け取ったら捨てて、区間2 用のものを新しく作る。

IP ヘッダーは、この先もずっと使う。宛先の `8.8.8.8` もまだ必要。そのため、捨てずに持っていき、必要な欄（TTL や、NAT なら送信元 IP）だけを直す。

### 付け替えでないと困る理由1：次の区間が Ethernet とは限らない

区間ごとに、使う通信の種類が違うことがある。

```text
 スマホ ──Wi-Fi── 家のルーター ──PPPoE── プロバイダ ──光回線── …
        ↑                    ↑
   Wi-Fi のヘッダー        PPPoE のヘッダー
   （アドレス欄が 3〜4 個） （Ethernet に別のヘッダーが足される）
```

Wi-Fi のヘッダーと PPPoE のヘッダーは、欄の数も並びも違う。「欄を書き換える」ことはできないので、**前の区間のヘッダーを外して、次の区間の形のヘッダーを付ける**しかない。IP ヘッダーはどの区間でも同じ形なので、書き換えで済む。

### 付け替えでないと困る理由2：新しい中身は、受け取ったヘッダーと関係なく決まる

区間2 の Ethernet ヘッダーの中身は、次のように決まる。

- 送信元 MAC：送り出す NIC（ens33）の MAC アドレス
- 宛先 MAC：ルーティングテーブルで決まった次の1台（`192.168.22.2`）の MAC アドレス。[近隣テーブル](../concepts/neighbor.md)（`ip neigh`）から引く

どちらも、受け取ったヘッダーの値を一切使わない。元の値を使わずに全部の欄を入れ直すので、「書き換え」と言っても実際には新しく作るのと同じ。

IP ヘッダーの書き換えは、ほとんどの欄（宛先 IP、プロトコル、ID など）を**そのまま残して**、一部だけ変える。

### Linux の中でも、実際にそうなっている

Linux カーネルは、パケットを受け取ると Ethernet ヘッダーを外し、IP ヘッダーから先だけを IP の処理に渡す。転送でも NAT でも、IP の処理をしている間、Ethernet ヘッダーはもう見ていない。送り出すときに、近隣テーブルの情報で新しい Ethernet ヘッダーを作って前に付ける。

### 「書き換えで良いのでは」という直感について

どちらの区間も Ethernet なら、結果だけ見ると「MAC の欄を2つ書き換えた」のと区別がつかない。実際、専用ルーターのチップ（ASIC）には、MAC の欄をその場で書き換える作りのものもある。直感は、結果としては間違っていない。

違いは、**考え方**（区間ごとに作り直すもの）と、**Ethernet 以外の区間にも対応できるか**にある。

## 質問65：MAC アドレスは NIC に付いている番号か

その通り。

| 用語 | 何か | たとえると |
|---|---|---|
| NIC | ネットワークにつなぐための部品（ens33、ens37 など） | 家の玄関 |
| MAC アドレス | NIC 1枚ごとに付いている番号 | 玄関に付いている表札 |
| IP アドレス | NIC に設定する住所（`10.0.0.1` など） | 郵便の住所 |

- NIC が2枚あれば、MAC アドレスも2つある。Router VM では、ens33 と ens37 がそれぞれ別の MAC アドレスを持つ。上の図の「送信元 MAC Router の ens33」は、「Router VM の ens33 という NIC の MAC アドレス」という意味
- `ip -br link` で、NIC ごとの MAC アドレスを見られる。`00:0c:29` で始まるのは、VMware が仮想 NIC に付けた番号
- MAC は Media Access Control の略。本来は「同じ線の上で、誰がいつ送るかを決める仕組み」の名前で、その仕組みで使う番号なので MAC アドレスと呼ぶ。会話では「MAC」だけで MAC アドレスを指すことが多い
- 実物の NIC では、MAC アドレスは工場で書き込まれている。世界で重ならないように、先頭の3バイトがメーカーごとに割り当てられている。ただし、OS の設定で別の値に変えることもできる
- IP アドレスは「最終的に誰へ」を表し、最初から最後まで変わらない。MAC アドレスは「この区間で次に誰へ」を表し、区間ごとに付け替えられる

## 確かめ方（NAT を設定した後）

Router VM で、ens37 と ens33 の `tcpdump` を別のターミナルで動かしたまま、Client VM から `ping -c 3 8.8.8.8` を送る。

```bash
sudo tcpdump -n -e -v -i ens37 icmp
sudo tcpdump -n -e -v -i ens33 icmp
```

予想：

- MAC アドレス（`-e` で表示）は、両側で違う
- 送信元 IP は、ens37 では `10.0.0.10`、ens33 では `192.168.22.129`
- TTL（`-v` で表示）は、ens37 では 64、ens33 では 63
- 宛先 IP（`8.8.8.8`）と ICMP の `id`・`seq` は、両側で同じ
