## 疑問

> **質問73**：firewall.md の「例A：SSH を許可したい」では、1行目に `tcp dport 22 accept` を書いているので、2行目の `ip saddr 192.168.22.0/24 drop` は読まれない、という認識で良いか？ 一方、例B では `ip saddr 192.168.22.0/24 drop` が適用されて `tcp dport 22 accept` は読まれないので、SSH は通らない、ということか？

> **質問74（追加の考え）**：rule を書く順番でファイアウォールの設定は大きく変わる。これから書くファイアウォール管理のソフトウェア（`routerd`）でも、この順番は非常に大事ではないか？

## 結論

| 質問 | 答え |
|---|---|
| 例A では rule 2 は読まれない？ | **SSH のパケットについては、そのとおり。** SSH 以外（ping など）は rule 1 に当たらないので、rule 2 まで進んで捨てられる |
| 例B では SSH は通らない？ | **192.168.22.0/24 から来た SSH は、そのとおり通らない。** それ以外のアドレス（たとえば LAN 側の 10.0.0.10）からの SSH は、rule 1 に当たらないので rule 2 で通る |
| ソフトウェアでも順番は大事？ | **大事。** 同じ rule の集まりでも、並べる順番で結果が変わる。ソフトウェアでは「順番をどう決めるか」と「順番どおりに反映されることをどう保証するか」を設計で決める必要がある |

どちらの質問にも共通するのは、**rule はパケットが来るたびに上から調べ直され、どこまで進むかはパケットごとに違う**こと。rule そのものが無視されるわけではない。

## 質問73：例A と例B

### 例A

```text
chain input {
    tcp dport 22 accept               ← rule 1
    ip saddr 192.168.22.0/24 drop     ← rule 2
}
```

| パケット | rule 1 | rule 2 | 結果 |
|---|---|---|---|
| 192.168.22.1 からの SSH | **当たる** → accept | 調べられない | 通る |
| 192.168.22.1 からの ping | 当たらない（ポート 22 ではない） | **当たる** → drop | 捨てる |

- SSH のパケットは rule 1 で決まるので、rule 2 まで届かない
- SSH のパケットは rule 2 の条件（送信元が 192.168.22.0/24）にも当てはまっている。それでも、上にある rule 1 が先に当たるので通る
- rule 1 に当たらないパケット（ping など）は rule 2 まで進んで捨てられる。rule 2 は「SSH 以外を止める rule」として働いている

### 例B

```text
chain input {
    ip saddr 192.168.22.0/24 drop     ← rule 1
    tcp dport 22 accept               ← rule 2
}
```

| パケット | rule 1 | rule 2 | 結果 |
|---|---|---|---|
| 192.168.22.1 からの SSH | **当たる** → drop | 調べられない | 捨てる |
| 192.168.22.1 からの ping | **当たる** → drop | 調べられない | 捨てる |
| 192.168.22.0/24 **以外**からの SSH（例：10.0.0.10 から） | 当たらない | **当たる** → accept | 通る |

- 192.168.22.0/24 から来たパケットは、rule 1 ですべて捨てられる。rule 2 まで届かないので、SSH は通らない
- ほかのアドレスからの SSH は rule 1 に当たらないので、rule 2 まで進んで通る。例B の rule 2 も、まったく使われないわけではない

### 例A と例B の違い

2つは**まったく同じ2行の rule** で、違うのは並び順だけ。

| パケット | 例A | 例B |
|---|---|---|
| 192.168.22.1 からの SSH | 通る | **捨てる** |
| 192.168.22.1 からの ping | 捨てる | 捨てる |
| 10.0.0.10 からの SSH | 通る | 通る |

並び順を入れ替えただけで、WAN 側からの SSH の結果が逆になる。このラボでは管理用の SSH が WAN 側から入っているので、例B の順番で反映すると Router VM から締め出される。

## 質問74：ソフトウェアで rule の順番を扱うとき

`routerd` の Firewall Management（Phase 6）でも、順番は大事になる。設計で考える必要があるのは、主に次の3つ。

### 1. 順番をどう決めるか

人間が1行ずつ書くなら、そのつど順番を考えられる。ソフトウェアが rule を作るときは、**順番の決め方そのもの**をルールにしておく必要がある。

一般的な決め方：

| 位置 | 置く rule | 理由 |
|---|---|---|
| 先頭 | `ct state established,related accept` | 返事を最初に通す。ほとんどのパケットがここで決まる |
| その次 | `ct state invalid drop` | おかしなパケットを早めに捨てる |
| 中ほど | **例外**（細かい条件の rule）：「SSH は許可」など | 大ざっぱな rule より先に当てる |
| 後ろ | **大ざっぱな rule**：「この範囲からは拒否」など | 例外に当たらなかったものだけをまとめて扱う |
| 最後 | policy（`drop`） | どれにも当たらなかったもの |

多くのファイアウォール管理ツール（ufw、firewalld など）も、利用者に順番を直接書かせず、ツールが決めた順番で rule を並べている。

### 2. 順番どおりに反映されることをどう保証するか

nftables への rule の足し方によって、入る位置が変わる。

| コマンド | 入る位置 |
|---|---|
| `nft add rule ...` | chain の**最後** |
| `nft insert rule ...` | chain の**先頭** |
| `nft add rule ... position <handle>` | 指定した rule の**後ろ** |
| `nft insert rule ... position <handle>` | 指定した rule の**前** |

1行ずつ足したり消したりすると、今の並びを毎回調べて正しい位置を計算する必要がある。計算を間違えれば、例B のように意図と違う結果になる。

そのため、よく使われるのは「**rule 全体を、決めた順番で毎回作り直して、まとめて置き換える**」方法。

```text
 設定（何を許可するか）
     │
     ▼
 決めた順番で、ruleset 全体を作る
     │
     ▼
 nft -f で、まとめて反映する（全部入るか、何も入らないかのどちらか）
```

- `nft -f` は、ファイルの中身を**1つのまとまり（トランザクション）**として反映する。途中で書き方の間違いがあれば、何も変わらない
- 1行ずつ反映すると、途中の一瞬だけ「SSH の許可が入る前に drop が入った」状態になりうる。まとめて反映すれば、その状態が生まれない
- 今の `/etc/nftables.conf` が `flush ruleset` で始まり、`nft -f` で読まれるのも、同じ考え方

### 3. 順番が正しいことをどう確かめるか

順番の間違いは、rule の書き方としては正しいので、`nft -c`（書き方の確認）では見つからない。確かめるには、**パケットを流して結果を見る**しかない。

- 例A・例B の表のように、「このパケットなら、どの rule に当たって、通るか捨てるか」を一覧にして、テストにする
- Phase 5 の Test Script や、Phase 6 の「VM 上で自動テスト」で、WAN 側からの SSH・ping、LAN 側からの通信などを実際に流して確かめる

### このラボでの位置づけ

ここに書いたのは一般的な考え方で、`routerd` の設計としてはまだ何も決めていない。順番の決め方と反映の方法は、Phase 6 で `routerd` の責務を決めるときに ADR として残す。labs/05 で手で rule を書く経験が、そのときの材料になる。
