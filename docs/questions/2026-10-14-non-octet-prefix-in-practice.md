# `/23` や `/15` のような中途半端な長さのネットワークは、実務で使うのか

## 疑問

> **質問31**：IP アドレスは `/24` や `/16` が、ちょうど区切りが良くて扱いやすい気がする。では、`/15` や `/23` のような中途半端なネットワークを、実務で構築することはあるのか？

> **質問32（追加質問）**：`/24` や `/16` などの区切りが良いネットワークアドレスは良いが、区切りが悪いネットワークを組むとき、ネットワークアドレスを計算したりするのか？

## 結論

| 質問 | 答え |
|---|---|
| 中途半端な長さを、実務で使う？ | **よく使う。** 長さは、区切りの良さではなく、**必要な台数**と**無駄の少なさ**で決める。クラウドの既定のサブネット（AWS・Google Cloud の `/20`）や、ISP から借りる固定 IP（`/29`）など、身近なところでも使われている |
| では、なぜ `/24` や `/16` をよく見るのか | **人間が読みやすいから。** 8 ビットの区切りが、10 進数の `.` の区切りと一致する。昔は `/8`・`/16`・`/24` しか使えなかった（クラス）名残もある。コンピューターにとっては、`/23` も `/24` も同じように扱える |
| `/15` のような大きいものは？ | **1 つの LAN としては、ほぼ作らない。** 台数が多すぎると、ブロードキャストが全員に届いて重くなるからである。ただし、アドレスの割り当て範囲や、複数のネットワークをまとめた経路としては、普通に出てくる |
| 区切りが悪いとき、ネットワークアドレスは計算する？ | **計算はする。ただし手で 2 進数を書くことは少ない。** 設計や設定の確認は `ipcalc` などの道具で行い、トラブル対応ではブロックサイズを使った暗算で見当をつける。そもそも新しく組むときは、先にネットワークアドレスを決めて、計算しやすいように設計する |

## なぜ `/24` や `/16` は「区切りが良い」と感じるのか

### 理由 1：10 進数の区切りと一致する

`/8`・`/16`・`/24` は、ネットワーク部とホスト部の境目が、ちょうど `.` の位置に来る。そのため、10 進数のままで範囲が読める。

| ネットワーク | 範囲 | 読みやすさ |
|---|---|---|
| `10.0.0.0/24` | `10.0.0.0`〜`10.0.0.255` | 変わるのは最後の数字だけ。前の 3 つの数字を見れば、同じネットワークかどうか一目で分かる |
| `10.0.0.0/23` | `10.0.0.0`〜`10.0.1.255` | 3 番目の数字が `0` と `1` にまたがる。2 進数で考えないと、範囲が分かりにくい |

`/23` の場合、`10.0.0.255` と `10.0.1.0` は、範囲の途中にある**普通の機器のアドレス**になる。「`.0` や `.255` だから特別、ではない」という[質問18](2026-10-13-network-address-in-routing-table.md#特別なのは0ではなくホスト部がすべて-0)の話が、実際に効いてくる場面である。

### 理由 2：昔は `/8`・`/16`・`/24` しか使えなかった

1993 年より前のインターネットでは、ネットワークの大きさが 3 種類（**クラス**）に決められていた。

| クラス | 今の書き方 | 機器に付けられる数 |
|---|---|---|
| クラス A | `/8` | 16,777,214 |
| クラス B | `/16` | 65,534 |
| クラス C | `/24` | 254 |

この仕組みでは、500 台をつなぎたい会社は、クラス C（254 台）では足りないのでクラス B（65,534 台）を受け取るしかなかった。**99% 以上のアドレスが使われないまま**になる。こうした無駄で、IPv4 アドレスが急速に減っていった。

そこで 1993 年に **CIDR**（サイダー、RFC 1519。今は RFC 4632）が決められ、`/0`〜`/32` の好きな長さを使えるようになった。500 台なら `/23`（510 台）で済む。`/24` のような書き方を「CIDR 表記」と呼ぶのは、ここから来ている。

今でも「クラス C」と言えば `/24` のこと、のような言い方を聞くことがある。それは、この時代の名残である。

### コンピューターにとっては、区切りは関係ない

カーネルは、IP アドレスとサブネットマスクを 1 ビットずつ重ねて計算している（[サブネットマスク](../concepts/ip-address.md#使い方ip-アドレスと重ねてネットワークアドレスを求める)）。`/23`（`255.255.254.0`）でも `/24`（`255.255.255.0`）でも、計算の手間は同じである。**「区切りが良い」のは、人間にとってだけ**である。

## 実務で使われる例

### 小さいもの（`/26`〜`/31`）：グローバル IP や、機器どうしの接続

| 長さ | 機器に付けられる数 | 使い道 |
|---|---|---|
| `/31` | 2 | ルーターどうしを 1 対 1 でつなぐ回線（RFC 3021。2 つとも機器に付ける） |
| `/30` | 2 | 同上（`/31` が使われる前からのやり方） |
| `/29` | 6 | **ISP から借りる固定のグローバル IP**。たとえば NTT の OCN の「IP8」プランは、IP アドレス 8 個（`/29`）。ISP 側との接続用にも 1 個使うので、機器に使えるのは 5 個という計算になる |
| `/28` | 14 | 同上（「IP16」プラン）。**AWS で作れるいちばん小さいサブネット**でもある |
| `/26`、`/27` | 62、30 | 小さなオフィスや、用途ごとに分けたサーバー用のネットワーク |

グローバル IP は数が限られていて、借りるとお金がかかる。そのため、**必要な分だけ細かく**借りる。

### 中くらい（`/20`〜`/23`）：台数の多い LAN や、クラウド

| 長さ | 機器に付けられる数 | 使い道 |
|---|---|---|
| `/23`、`/22` | 510、1,022 | 社員が多いフロアや、Wi-Fi のネットワーク（スマホやノート PC で台数が増えやすい）。254 台では足りないときに使う |
| `/20` | 4,094 | **クラウドの既定のサブネット**。AWS のデフォルト VPC（`172.31.0.0/16`）は、アベイラビリティーゾーンごとに `/20` のサブネットを作る。Google Cloud の自動モードの VPC も、リージョンごとに `/20`（例：`us-central1` は `10.128.0.0/20`） |

> 💡 「機器に付けられる数」は、サービスによって少し変わる。AWS は、各サブネットの先頭 4 個と最後の 1 個、合わせて 5 個を予約している（ネットワークアドレス、ルーター、DNS、予備、ブロードキャストアドレス）。そのため `/20` なら 4,091 個、`/28` なら 11 個しか使えない。

### 大きいもの（`/9`〜`/15`）：LAN ではなく「範囲」として

`/15` のような大きな長さは、1 つの LAN としてはまず作らない。その代わり、**「ここからここまでを、このために使う」という範囲**として、よく出てくる。

| 範囲 | 何か |
|---|---|
| `172.16.0.0/12` | **プライベート IP の範囲そのもの**（`172.16.0.0`〜`172.31.255.255`）。決まりの時点で、すでに中途半端な長さである |
| `100.64.0.0/10` | ISP が使う「キャリアグレード NAT」用の範囲（RFC 6598）。Tailscale の `100.x.y.z` のアドレスも、この範囲から使っている |
| `10.96.0.0/12` | Kubernetes（kubeadm）で、サービス用に使うアドレスの既定の範囲 |
| `10.128.0.0/9` | Google Cloud の自動モードの VPC が、各リージョンの `/20` を切り出す元の範囲 |

### 経路をまとめる（経路集約）

複数のネットワークを、**ルーティングテーブルの 1 行にまとめる**ときにも、中途半端な長さが出てくる。

```text
10.0.0.0/24 ─┐
10.0.1.0/24 ─┤ まとめると
10.0.2.0/24 ─┤ 10.0.0.0/22 via 192.168.22.129（1 行で済む）
10.0.3.0/24 ─┘
```

たとえば将来、VLAN（labs/09）で Router VM の内側に LAN を 4 つ作ったとする。外側の機器には、4 行ではなく `10.0.0.0/22` の 1 行で「この範囲は Router VM に渡して」と教えられる。

インターネットのルーターも、こうしてまとめた経路を使っている。CIDR の目的は、アドレスの無駄を減らすことと、もう 1 つ、**インターネット全体のルーティングテーブルが増えすぎないようにすること**だった（RFC 4632）。

### なぜ `/15` のような大きな LAN は作らないのか

1 つの LAN の中では、ARP や DHCP の**ブロードキャストが全員に届く**（[質問23](2026-10-13-network-address-in-routing-table.md#質問231000255-はネットワーク内の全員に対する宛先か)）。`/15` なら 13 万台以上が 1 つの LAN に入り、誰かが ARP で呼びかけるたびに、全員がそれを受け取ることになる。トラブルが起きたときも、影響が LAN 全体に広がる。

そのため、1 つの LAN は数百〜1,000 台くらい（`/24`〜`/22`）に抑えて、それより多いときはルーターや VLAN で分けるのが一般的である。

## 中途半端な長さを使うときの注意

| 注意点 | 説明 |
|---|---|
| **始まりのアドレスが決まっている** | `/23` のネットワークアドレスは、3 番目の数字が**偶数**になる。`10.0.0.0/23` は正しいが、`10.0.1.0/23` はホスト部が 0 ではないので、ネットワークアドレスにならない。`/22` なら 4 の倍数になる |
| **`.0` や `.255` が普通のアドレスになる** | `10.0.0.0/23` では、`10.0.0.255` と `10.0.1.0` を機器に付けられる。「`.255` はブロードキャスト」と思い込んでいると、間違える |
| **計算は道具に任せる** | 2 進数の計算は間違えやすい。`ipcalc` などの道具で確かめる |
| **後から大きさを変えにくい** | 大きさを変えるには、すべての機器のサブネットマスクと、ルーターやファイアウォールの設定を変える必要がある。将来の台数の増加を見込んで、少し余裕を持たせる |

場面によって、選び方も変わる。

| 場面 | 選び方 |
|---|---|
| グローバル IP（ISP から借りる） | 数が限られ、お金もかかるので、**必要な分だけ**（`/29`、`/28` など） |
| 社内のプライベート IP | `10.0.0.0/8` は広いので、**読みやすさを優先して `/24`** を選ぶことも多い。足りなければ `/23`・`/22` |
| クラウド | VPC 全体の範囲が限られるので、サブネットごとに必要な大きさを決める。サービスが予約するアドレスの数にも注意する |

## 質問32：ネットワークアドレスは計算するのか

### 結論

**計算はする。ただし、毎回 2 進数を手で書いて計算するわけではない。** 実務では、主に次の 3 つの方法を組み合わせる。

| 方法 | 使う場面 |
|---|---|
| **① 道具に計算させる**（`ipcalc`、プログラム、管理ツール） | 設計するとき、設定を書く前の確認。**いちばん確実** |
| **② 暗算のコツ**（ブロックサイズ） | トラブル対応中に、「この IP はどのネットワークか」をすぐ知りたいとき |
| **③ そもそも、計算しやすいように設計する** | ネットワークを新しく組むとき |

また、機器に `10.0.5.77/23` のように設定すれば、ネットワークアドレス自体はカーネルが自動で計算する（`ip route` に `10.0.4.0/23` の行ができる）。人間が計算するのは、**設計と確認のため**である。

### ① 道具に計算させる

`ipcalc` なら、ネットワークアドレス・機器に付けられる範囲・ブロードキャストアドレスが一度に出る。

```bash
ipcalc 10.0.5.77/23
```

プログラムでも計算できる。Python なら、標準ライブラリの `ipaddress` を使う。

```python
>>> import ipaddress
>>> net = ipaddress.ip_interface("10.0.5.77/23").network
>>> net
IPv4Network('10.0.4.0/23')
>>> net.broadcast_address
IPv4Address('10.0.5.255')
>>> net.num_addresses
512
```

多くの言語に、同じような道具がある。将来ルーターのソフトウェアを自作するときも、自分でビット計算を書くより、まずこうした標準の道具を使うのが安全である。

会社のネットワークでは、どのネットワークをどこで使っているかを、**IPAM**（IP アドレス管理ツール。NetBox など）や表計算で管理していることが多い。範囲の計算も、そこで行う。

### ② 暗算のコツ：ブロックサイズ

境目がある数字（サブネットマスクが `255` でも `0` でもない位置）だけを見る。

1. **ブロックサイズ = 256 − その位置のマスクの値**
2. ネットワークアドレスは、**ブロックサイズの倍数**になる
3. IP アドレスの数字を超えない、いちばん近い倍数が、ネットワークアドレス

| 例 | 境目の位置 | ブロックサイズ | ネットワークアドレス |
|---|---|---|---|
| `10.0.5.77/23`（`255.255.254.0`） | 3 番目（`254`） | 256 − 254 = 2 | 5 を超えない 2 の倍数は 4 → **`10.0.4.0`** |
| `192.168.1.100/26`（`255.255.255.192`） | 4 番目（`192`） | 256 − 192 = 64 | 100 を超えない 64 の倍数は 64 → **`192.168.1.64`** |

2 進数を書かなくても、引き算と倍数だけで求められる。手順の詳しい説明と例は、[ip-address.md（ネットワークアドレスを暗算で求める）](../concepts/ip-address.md#ネットワークアドレスを暗算で求める) にまとめた。

### ③ 計算しやすいように設計する

ネットワークを**新しく組む**ときは、「IP アドレスからネットワークアドレスを求める」のではなく、**先にネットワークアドレスを決めて**、そこから機器に IP を割り当てる。

たとえば、ある拠点に `10.0.0.0/22`（`/24` を 4 つ分）を割り当てたとする。それを次のように分けておけば、計算はほとんど要らない。

| 用途 | ネットワーク |
|---|---|
| 社員の PC（台数が多い） | `10.0.0.0/23`（`10.0.0.0`〜`10.0.1.255`） |
| サーバー | `10.0.2.0/24` |
| 予備 | `10.0.3.0/24` |

設計で気をつけるのは、**始まりのアドレスを、ブロックサイズの倍数にそろえる**ことである。`/23` なら、3 番目の数字を偶数から始める。これを守っておけば、あとで計算や確認もしやすくなる。

### 人間が計算・確認する場面

| 場面 | 何を確かめるか |
|---|---|
| 設計 | 始まりのアドレスがそろっているか、ほかのネットワークと範囲が重なっていないか |
| ファイアウォールや経路の設定を書く | `10.0.4.0/23` のように、正しいネットワークアドレスで書けているか。間違えると、`Invalid prefix` のエラーになるか、意図しない範囲になる |
| トラブル対応 | 2 台の機器が同じネットワークにいるか、サブネットマスクが食い違っていないか |

## まとめ

- `/23` や `/20`、`/29` のような中途半端な長さは、**実務でよく使う**。長さは、区切りの良さではなく、**必要な台数**と**無駄の少なさ**で決める。
- `/24` や `/16` が多く見えるのは、**10 進数の区切りと一致して人間が読みやすいから**。昔は `/8`・`/16`・`/24` しか使えなかった（クラス）名残もある。1993 年の CIDR から、好きな長さを使えるようになった。
- 小さいものは、グローバル IP（ISP の `/29` など）やルーターどうしの接続（`/30`、`/31`）。中くらいのものは、台数の多い LAN（`/23`、`/22`）やクラウドの既定のサブネット（`/20`）。
- `/15` のような大きいものは、1 つの LAN としては作らない（ブロードキャストが全員に届いて重くなる）。その代わり、アドレスの範囲（`172.16.0.0/12`、`100.64.0.0/10` など）や、経路をまとめるときに出てくる。
- 中途半端な長さでは、**始まりのアドレスが決まっている**ことと、**`.0` や `.255` が普通のアドレスになる**ことに注意する。計算は `ipcalc` などの道具で確かめる。
- ネットワークアドレスの計算は、設計や確認では**道具**（`ipcalc`、Python の `ipaddress`、IPAM）に任せ、トラブル対応では**ブロックサイズ**（256 − マスクの値）で暗算する。新しく組むときは、**始まりのアドレスをブロックサイズの倍数にそろえて**、計算しやすいように設計する。
