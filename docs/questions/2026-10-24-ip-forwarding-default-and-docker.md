## 疑問

> **質問45**：IP フォワードは、ルーターの機能として実際にあるのか？ 初期状態でオンが普通なのか？

> **質問46**：今回は Debian（OS）の機能で IP フォワードをした。この仕組みは、ルーターの仕組みと同じか？ ルーティングテーブルをもとにパケットを送っているのか？

> **質問47（追加質問）**：サーバーの IP フォワードがオンだと、LAN につながる NIC と WAN につながる NIC があるサーバーでは、WAN と LAN の間に道ができて、セキュリティ的に危ない気がする。それなのに、必要なソフトウェアが自動で転送をオンにする、というところが引っかかった。Docker は、Linux の IP フォワードを `1` にするのか？ これはかなり問題だと考える。また、コンテナから外へ通信するというのは、どこに通信する想定か？

## 結論

| 質問 | 答え |
|---|---|
| IP フォワードは、ルーターの機能として実際にある？ | **ある。むしろ転送はルーターの本業そのもの**である。名前や設定の仕方は機器によって違うが、「自分宛てではないパケットを、別の口から送り出す」という動きは同じ |
| 初期状態でオンが普通？ | **機器の種類による。** ルーターは最初からオン。普通の PC・サーバー（Linux、Windows、macOS）は**オフ**で、それが正しい。意図しない転送は、ネットワークの間に抜け道を作ってしまうからである |
| Debian の転送は、ルーターの仕組みと同じ？ | **考え方（手順）は同じ。** どちらも「ルーティングテーブルで出口を決める → TTL を 1 減らす → MAC アドレスを付け替える → 送り出す」という手順で転送する。違うのは、その手順を**誰が処理するか**（Linux は CPU、大型の専用ルーターは専用チップ） |
| ルーティングテーブルで送っている？ | **その通り。** labs/02 では、宛先 `192.168.22.2` が `192.168.22.0/24 dev ens33` の行に当てはまったので、ens33 から送り出された |
| Docker は `ip_forward` を `1` にする？ | **する。** Docker は起動時に `net.ipv4.ip_forward` を `1` にする |
| それは問題では？ | **心配は正しい。** そのため Docker は、転送をオンにするときに、ファイアウォールで「転送は原則すべて捨てる」設定にし、コンテナの通信だけを許可する。ただし、実務で問題になる落とし穴もある |
| コンテナはどこと通信する？ | コンテナ → 外：インターネット（`apt install`、外部の API など）、社内の別サーバー（DB など）。外 → コンテナ：`docker run -p` で公開した Web サーバーなどへのアクセス。**どちらの向きでも転送が起きる** |

## 質問45：IP フォワードは、ルーターの機能として実際にあるのか

### 転送はルーターの本業

ルーターとは、「**ネットワークとネットワークの間で、パケットを転送する機器**」のことである。labs/02 で `ip_forward` を `1` にした Router VM は、まさにその動きをした。

```text
LAN からパケットが届く
   ↓
ルーターが受け取る
   ↓
自分宛て？ ── はい ──→ 自分で受け取る（ping の返事など）
   ↓ いいえ
転送する ──→ WAN へ送り出す
```

専用のルーターでは、この「転送する」が最初から有効になっている。そもそも転送するための機器なので、転送しないルーターでは意味が無い。

### 初期状態は、機器の種類で分かれる

| 機器 | 転送の初期状態 | 理由 |
|---|---|---|
| **ルーター**（家庭用ルーター、Cisco、YAMAHA の RTX など） | **オン** | 転送するための機器だから |
| **L3 スイッチ** | 機種による。オフで、設定でオンにするものも多い | スイッチ（同じネットワークの中の中継）としても使えるため |
| **普通の PC・サーバー**（Linux、Windows、macOS） | **オフ** | ルーターではないので、転送しないのが正しい |
| **このラボの Router VM**（Debian） | **オフ**（`net.ipv4.ip_forward = 0`） | 中身は普通の Linux なので、PC・サーバーと同じ |

### なぜ PC・サーバーではオフなのか

NIC を 2 つ持つサーバーで転送がオンになっていると、**2 つのネットワークの間に、誰も意図していない通り道ができる**。

```text
  インターネット側                  サーバー                      社内 LAN 側
                         +--------------------------+
  攻撃者  ──→  eth0  ──→ | ip_forward = 1           | ──→  eth1  ──→  社内のサーバー
                         | 自分宛てではないので転送 |
                         +--------------------------+
                    ↑ ルーターのつもりは無いのに、通り道になってしまう
```

そのため、インターネットの通信の決まりでも、ホスト（ルーターではない機器）の転送機能は**初期状態で無効にしておく**ことが求められている（RFC 1122）。Linux の `ip_forward` が初期状態で `0` なのは、この決まりに従っているからである。

## 質問46：Debian の転送は、ルーターの仕組みと同じか

### 転送の手順は同じ

labs/02 で、Router VM の中では次のことが起きていた。

```text
① ens37 で受け取る
     MAC の宛先：Router VM（00:0c:29:73:2d:6b）
     IP の宛先 ：192.168.22.2（Router VM ではない）
        ↓
② IP の宛先が自分ではない → ip_forward = 1 なので転送する
        ↓
③ ルーティングテーブルで出口を探す
     192.168.22.2 → 「192.168.22.0/24 dev ens33」の行に当てはまる
        ↓
④ TTL を 1 減らす（64 → 63）
        ↓
⑤ 近隣テーブル（ARP）で 192.168.22.2 の MAC を調べ、MAC アドレスを付け替える
     送信元 MAC：Router VM の ens33
     宛先 MAC  ：VMware NAT
        ↓
⑥ ens33 から送り出す
```

**専用ルーターも、この①〜⑥と同じ手順で転送している。** IP アドレスはそのままで、MAC アドレスを区間ごとに付け替えながら、ルーティングテーブルに従って次へ渡していく。これがルーターの基本的な動きである。

### パケットの見た目の変化

```text
           Client VM ──(LAN)──→ Router VM ──(WAN)──→ VMware NAT

LAN 区間（ens37 で見えたもの）
  MAC：00:0c:29:20:6c:ff（Client VM）→ 00:0c:29:73:2d:6b（Router VM の ens37）
  IP ：10.0.0.10 → 192.168.22.2
  TTL：64

WAN 区間（ens33 から出たもの）
  MAC：00:0c:29:73:2d:61（Router VM の ens33）→ VMware NAT の MAC   ← 付け替わる
  IP ：10.0.0.10 → 192.168.22.2                                       ← そのまま
  TTL：63                                                             ← 1 減る
```

labs/02 の観察では、IP アドレスがそのままであることは確認した。MAC アドレスと TTL の変化は、まだ自分の目では確かめていない（[まだ試していないこと](#まだ試していないこと)）。

### 違うのは「誰が処理するか」

| | Linux（このラボの Router VM） | 大型の専用ルーター |
|---|---|---|
| 転送の手順 | ①〜⑥ | ①〜⑥（同じ） |
| ルーティングテーブルを使う？ | 使う | 使う |
| 誰が処理するか | **カーネル**（CPU が、転送用のプログラムを実行する） | **専用のチップ**（ASIC。転送用に作られた回路） |
| 速さ | 家庭や小さな拠点の通信量なら十分 | 非常に大量のパケットを処理できる |

専用ルーターがなぜ専用チップを使うのかは、[専用ルーターはなぜ仕事を 2 つに分けるのか：CPU と ASIC の違い](2026-10-24-router-cpu-vs-asic.md) にまとめた。

### Linux で動いているルーターは実際に多い

- **家庭用ルーター**の多くは、中身が Linux である
- **OpenWrt**（家庭用ルーター向け）、**VyOS**（企業向け）など、Linux をもとにしたルーター用の OS がある
- 大型の専用ルーターでも、経路の計算や設定を担当する部分は Linux で動いていることがある

このリポジトリで「Debian をルーターにする」のは、こうした実際のルーターと同じ土台の上で、仕組みを学ぶことになる。

## 質問47：Docker は `ip_forward` を `1` にするのか

### する

Docker（`dockerd`）は、起動時に `net.ipv4.ip_forward` を `1` にする。Docker の設定（`--ip-forward=false`）で止めることもできるが、その場合はコンテナから外へ通信できなくなる。

### なぜ転送が必要なのか

コンテナは、**ホストの中にある別のネットワーク**にいる。

```text
Docker ホスト（Linux）の中
────────────────────────────────────────────────────────────────
  コンテナ          docker0                    eth0
  172.17.0.2  ──→  172.17.0.1  ──（転送）──→  192.168.1.10  ──→  LAN / インターネット
                   （ホスト内の LAN）          （ホストの外側）
────────────────────────────────────────────────────────────────
```

コンテナが外へ送ったパケットは、ホストの docker0 で受け取られ、eth0 から出ていく。ホストのカーネルから見ると、**「自分に渡されたが、自分宛てではない」パケット**である。labs/02 で見た Router VM とまったく同じ状況なので、転送がオンでないと捨てられてしまう。

さらに Docker は、送信元をホストの eth0 の IP に書き換える **NAT（masquerade）**も設定する。これが無いと、labs/02 の Experiment 3 と同じく、帰り道が無くて返事が戻らない。

### Docker ホストは「NAT ルーター」になっている

このラボの構成と並べると、同じ形をしている。

| このラボ | Docker ホスト | 役割 |
|---|---|---|
| Client VM（`10.0.0.10`） | コンテナ（`172.17.0.2`） | 内側の機器 |
| Router VM の ens37（`10.0.0.1`） | docker0（`172.17.0.1`） | 内側の口（LAN） |
| Router VM の ens33（`192.168.22.129`） | eth0（`192.168.1.10`） | 外側の口（WAN） |
| `ip_forward = 1`（labs/02） | Docker が `ip_forward = 1` にする | 転送 |
| NAT（labs/04） | Docker が masquerade を設定する | 帰り道を作る |
| ファイアウォール（labs/05） | Docker がルールを設定する | 通してよいものを決める |

つまり、Docker をインストールしたサーバーは、知らないうちに「**Docker が管理する NAT ルーター**」になっている。

### コンテナはどこと通信するのか

| 向き | 通信先の例 | 転送 |
|---|---|---|
| **コンテナ → 外** | インターネット（`apt install`、`pip install`、外部の API）、社内の別サーバー（DB、認証サーバー）、クラウドのサービス | docker0 → eth0 |
| **外 → コンテナ** | `docker run -p 8080:80` で公開した Web サーバーなどへのアクセス。ホストの 8080 番で受けて、コンテナの 80 番へ届ける | eth0 → docker0 |

```text
コンテナ → 外
  コンテナ（172.17.0.2）→ docker0 →（転送・NAT）→ eth0 → インターネット

外 → コンテナ（-p 8080:80 の場合）
  利用者 → eth0 の 8080 番 →（宛先をコンテナの 80 番に書き換え・転送）→ docker0 → コンテナ（172.17.0.2:80）
```

どちらの向きでも、ホストを通り抜けるので転送が起きる。

### セキュリティ上の問題はないのか

「転送がオンになると、LAN と WAN の間に道ができる」という心配は正しい。そこで Docker は、**転送をオンにするときに、ファイアウォール（iptables）の FORWARD の初期方針を DROP（すべて捨てる）にする**。そのうえで、コンテナの通信だけを通すルールを足す。

```text
           転送してよいか                    通してよいか
パケット ──→ ip_forward = 1  ──→  FORWARD（初期方針：DROP） ──→ 送り出す
            （Docker がオン）       │
                                    ├─ コンテナの通信 → Docker のルールで許可 → 通る
                                    └─ それ以外       → DROP              → 捨てる
```

labs/02 の Result に書いた「ルーターの役割の分担」が、ここでも効いている。

| 役割 | 担当 | Docker の場合 |
|---|---|---|
| 転送してよいか | `ip_forward` | `1`（オン） |
| どこへ送るか | ルーティングテーブル | docker0 / eth0 の経路 |
| **通してよいか** | **ファイアウォール** | **原則 DROP、コンテナの通信だけ許可** |

**`ip_forward` は「転送してもよい」というスイッチにすぎない。** 実際に何を通すかは、ファイアウォールで決める。転送がオンでも、ファイアウォールで絞っていれば「何でも通る抜け道」にはならない。

### それでも実務で問題になる落とし穴

| 落とし穴 | 何が起きるか |
|---|---|
| **公開したポートが、ホストのファイアウォール（ufw など）を素通りする** | Docker のルールが ufw のルールより先に評価されるため、ufw で閉じたつもりのポートが、外から見えてしまう。Docker の公式ドキュメントでも注意されている |
| **同じホストの、別の仕組みの通信が止まる** | FORWARD が DROP になるので、Docker 以外の転送（ホスト上の VM、自分で作ったブリッジなど）が通らなくなる |
| **転送がオンになっていることに気づかない** | 「このサーバーはルーターではない」と思い込んでいると、転送がオンになっていることを前提にした確認が抜ける |

そのため、実務では Docker を入れたサーバーで次のことを行う。

- `sysctl net.ipv4.ip_forward` と、ファイアウォールのルール（`sudo iptables -L FORWARD -n -v` など）を確認する
- 公開するポートは、`-p 127.0.0.1:8080:80` のように、必要な範囲に絞る（この例は、ホストの中からしかアクセスできない）
- 自分で追加したいルールは、Docker が用意している **`DOCKER-USER` チェーン**に書く（Docker のルールより先に評価される）

### Docker 以外にも、転送をオンにするソフトウェアがある

| ソフトウェア | 転送をオンにする理由 |
|---|---|
| Docker、Podman | コンテナを外とつなぐため |
| Kubernetes のノード | Pod（コンテナ）どうしや、外とつなぐため |
| VPN サーバー（WireGuard、OpenVPN など） | VPN でつないだ相手を、社内 LAN へ通すため |
| 仮想化（libvirt / KVM の NAT ネットワーク） | VM を外とつなぐため |

どれも、**ホストの中に「別のネットワーク」を作り、それを外とつなぐ**ソフトウェアである。

## まとめ

- **転送は、ルーターの本業そのもの**である。専用ルーターでは最初からオン、普通の PC・サーバー（Linux を含む）では**オフ**が初期状態である。
- PC・サーバーで転送がオフなのは、**意図しない通り道を作らないため**である。NIC を 2 つ持つサーバーで転送がオンだと、2 つのネットワークの間に抜け道ができる。
- Debian の転送と専用ルーターの転送は、**手順が同じ**である。どちらも、ルーティングテーブルで出口を決め、TTL を 1 減らし、MAC アドレスを付け替えて送り出す。IP アドレスは書き換えない。違うのは、処理するのが CPU（カーネル）か、専用チップかである。
- **Docker は `ip_forward` を `1` にする。** コンテナはホストの中の別のネットワーク（docker0）にいるので、外との通信には転送と NAT が必要になる。Docker ホストは、Docker が管理する **NAT ルーター**になっている。
- その代わり Docker は、ファイアウォールの FORWARD を**原則 DROP** にして、コンテナの通信だけを通す。**`ip_forward` は「転送してもよい」というスイッチにすぎず、何を通すかはファイアウォールが決める。**
- ただし、公開したポートが ufw を素通りするなどの落とし穴がある。Docker を入れたサーバーでは、転送の設定とファイアウォールのルールを確認する。
