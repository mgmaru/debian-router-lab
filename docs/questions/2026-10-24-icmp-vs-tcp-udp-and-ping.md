## 結論

| 質問 | 答え |
|---|---|
| ICMP は UDP？ | **違う。** ICMP は TCP とも UDP とも別の、独立したプロトコルである。3 つとも IP パケットの中に直接入って運ばれる |
| TCP なら 3 ウェイハンドシェイクが見られる？ | **見られる。** `tcpdump` では `Flags [S]` → `[S.]` → `[.]` と表示される |
| Client VM から TCP を送れる？ | **送れる。** `ping` のような専用コマンドは無いが、TCP を使うプログラム（`ssh`、`nc` など）で接続すれば、それが TCP のパケットになる。ただし、相手側でそのポートを待ち受けているプログラムが必要 |
| ping 用のポートが空いている？ | **ICMP にポートは無い。** ping が通って TCP が通らない主な原因は、①そのポートで待ち受けているプログラムがいない、②ファイアウォールが ICMP は許可して、TCP のそのポートは止めている、のどちらかである |
| ping はソケットを作らない？ | **作る。** 送る側の `ping` コマンドは、ICMP 用のソケットを作る。ソケットの住所が「IP ＋ ポート」になるのは TCP・UDP の場合で、ICMP のソケットの住所は **IP だけ**である |
| ping にサーバーは無い？ | **無い。** 受ける側では、**OS のカーネルが自分で返事をする**。プログラムの起動もソケットも要らない |
| ping は ICMP で、OS が直接応答する？ | **その通り。** 正確には、ICMP の echo request / echo reply を使い、受ける側では OS の中の**カーネル**が返事をする。ただし、カーネルの設定やファイアウォールで止められていると返事をしない |
| ping のソケットは誰が、いつ作る？ | **送る側の `ping` コマンドが、実行した直後に**カーネルに頼んで作る。返事を `ping` コマンドに渡す窓口が必要だからである。**受ける側は作らない**（カーネルの中だけで処理が終わる）。「作る必要が無い」のは受ける側である |
| TCP・UDP は、クライアントもサーバーもソケットを作る？ | **その通り。** TCP のサーバーは、起動時に**待ち受け用**のソケットを 1 つ作り、接続を受け入れるたびに**通信用**のソケットを 1 つずつ作る。UDP のサーバーは、1 つのソケットで全員とやりとりする |
| ping が通っても、TCP・UDP が届くとは限らない？ | **その通り。** TCP・UDP には、**ファイアウォール**（そのポートが許可されているか）と**待ち受け**（受け取るプログラムがいるか）という、ping には無い関門がある。UDP はハンドシェイクが無いので、特に確かめにくい |
| ICMP は OSI 参照モデルのどの層？ | **ネットワーク層（第 3 層）。** IP と同じ層である。パケットの形では TCP・UDP と同じく IP の中に入っているが、役割は「IP の配送の状態を知らせる、IP の付属品」なので、IP の仲間に分類される |

**ping が通っても、TCP が通るとは限らない。** ping で分かるのは「OS とネットワークが生きていること」までで、「サービスが動いていること」は分からない。

## ICMP・UDP・TCP の違い

### 3 つとも IP の上に乗っている

```text
IPパケット
├─ IPヘッダ（「中身は何か」をプロトコル番号で示す）
└─ 中身：ICMP（1番） / TCP（6番） / UDP（17番） のどれか
```

IP ヘッダには「中身のプロトコル番号」という項目がある。受け取ったカーネルは、この番号を見て、ICMP・TCP・UDP のどの処理に渡すかを決める。

### 比較表

| | ICMP | UDP | TCP |
|---|---|---|---|
| プロトコル番号 | 1 | 17 | 6 |
| 役割 | ネットワークの**連絡・エラー通知** | データを**投げっぱなし**で送る | データを**確実に、順番どおり**届ける |
| ポート番号 | **無い** | ある | ある |
| 接続（ハンドシェイク） | 無い | 無い | ある（3 ウェイハンドシェイク） |
| 届いたかの確認・再送 | 無い | 無い | ある |
| 受ける側で返事をするのは | **カーネル**（ping の場合） | 待ち受けているプログラム | 待ち受けているプログラム |
| 受ける側の準備 | **不要** | プログラムの起動が必要 | プログラムの起動が必要 |
| 主な用途 | `ping`、`traceroute`、エラーの通知 | DNS、DHCP | SSH、HTTP |

### ヘッダの中身

ポート番号は、TCP と UDP の**ヘッダにある項目**である。ICMP のヘッダには、その項目自体が無い。

| ICMP（ping の場合） | UDP | TCP |
|---|---|---|
| タイプ（8 = echo request、0 = echo reply） | 送信元ポート | 送信元ポート |
| コード | 宛先ポート | 宛先ポート |
| チェックサム | 長さ | シーケンス番号 |
| **id**（どの ping か） | チェックサム | 確認応答番号（ACK） |
| **シーケンス番号**（何回目か） | | フラグ（SYN、ACK、RST など） |
| | | ウィンドウサイズ など |

### ICMP は「連絡・エラー通知」用

ICMP は、データを運ぶためではなく、**ネットワークの状態を知らせるため**のプロトコルである。`ping` の echo request / echo reply は、その一部にすぎない。

| ICMP のタイプ | 意味 | 使われる場面 |
|---|---|---|
| 8 / 0 | echo request / echo reply | `ping` |
| 3 | Destination Unreachable（宛先に届かない） | 経路が無い、ポートで誰も待ち受けていない（UDP）、ファイアウォールが拒否した |
| 11 | Time Exceeded（TTL が切れた） | `traceroute` がこれを利用する |

TCP や UDP の通信でも、うまくいかなかったときの知らせに ICMP が使われる。

### `tcpdump` での見え方

ICMP（labs/01 の Experiment 9）：ポート番号が無く、`id` と `seq` で見分ける。

```text
IP 10.0.0.10 > 10.0.0.1: ICMP echo request, id 1, seq 1, length 64
IP 10.0.0.1 > 10.0.0.10: ICMP echo reply, id 1, seq 1, length 64
```

TCP：アドレスの後ろに `.ポート番号` が付く。

```text
IP 10.0.0.1.42784 > 10.0.0.10.22: Flags [P.], ... length 52
         ↑ 送信元ポート       ↑ 宛先ポート（22 = SSH）
```

## 質問44：ICMP は OSI 参照モデルのどの層か

一般的には、**ICMP はネットワーク層（第 3 層）**、つまり IP と同じ層に分類される。

### 階層図

```text
  OSI 参照モデル                  TCP/IP モデル           このラボで出てきたもの
+--------------------------+    +--------------------+
| 7 アプリケーション層     |    |                    |
+--------------------------+    |                    |
| 6 プレゼンテーション層   |    | アプリケーション層 |    SSH、HTTP、DNS、DHCP
+--------------------------+    |                    |
| 5 セッション層           |    |                    |
+--------------------------+    +--------------------+
| 4 トランスポート層       |    | トランスポート層   |    TCP、UDP
+--------------------------+    +--------------------+
| 3 ネットワーク層         |    | インターネット層   |    IP、ICMP  ← ここ
+--------------------------+    +--------------------+    ARP（2 と 3 の間）
| 2 データリンク層         |    |                    |    Ethernet、MAC アドレス
+--------------------------+    |                    |
| 1 物理層                 |    | リンク層           |    ケーブル、NIC
+--------------------------+    +--------------------+
```

OSI 参照モデルは、通信を説明するための 7 階層のモデルである。インターネットで実際に使われているのは、それを 4 階層にまとめた **TCP/IP モデル**で、ICMP は IP と同じ「インターネット層」に入る。

### なぜネットワーク層なのか

層は「パケットの中で、どこに入っているか」ではなく、**何の役割をしているか**で決まる。

| | ICMP | TCP・UDP |
|---|---|---|
| 役割 | **IP の付属品**。IP の配送がうまくいったかを知らせる（届かない、TTL が切れた、など） | アプリケーションのデータを、相手のプログラムまで運ぶ |
| 誰のためのものか | ネットワーク（IP）自身 | アプリケーション |
| ポート番号（プログラムの区別） | 無い | ある |

ICMP の仕様書（RFC 792）にも、「ICMP は実際には IP の不可欠な一部であり、すべての IP の実装が持たなければならない」と書かれている。IP が自分の状態を知らせるための仕組みなので、IP と同じネットワーク層に入れられている。

### 形と役割がずれている

```text
パケットの形（入れ子）               役割による分類
+--------------------+
| IPヘッダ           |  ← 第3層       IP、ICMP  ← 第3層（ネットワーク層）
+--------------------+
| ICMP / TCP / UDP   |  ← 中身        TCP、UDP  ← 第4層（トランスポート層）
+--------------------+
```

形の上では TCP・UDP と同じ位置にあるのに、役割の上では IP の仲間である。教科書によっては、この中途半端さを「第 3 層と第 4 層の間」と説明することもある。

ARP も似た立場にある。役割は IP アドレスから MAC アドレスを調べることで、IP を助けている（[neighbor.md](../concepts/neighbor.md)）。ただし、IP には入らず Ethernet に直接入るので、「第 2 層と第 3 層の間」と説明されることがある。

### 実務での言い方

- 「**L3 の疎通**は取れている」＝ ping（ICMP）が通る。IP で届くことは確認できている
- 「**L4 の疎通**が取れない」＝ TCP・UDP のポートにつながらない

[質問36](#質問36ping-が通るのに-tcp-が通らない原因) の「ping は通るのに TCP は通らない」は、まさにこの「L3 は OK、L4 が NG」の状態である。

## 質問34・35：TCP の 3 ウェイハンドシェイク

TCP は、データを送る前に、3 つのパケットで「接続」を作る。

```text
クライアント                      サーバー（22番で待ち受け）
     │ ── SYN ─────────────────→ │   「つなぎたい」
     │ ←──────────────── SYN+ACK │   「いいよ。こちらからも」
     │ ── ACK ─────────────────→ │   「了解」
     │                           │
     │ ←── データのやりとり ───→  │
```

`tcpdump` では、フラグが次のように表示される。

| 表示 | フラグ | 意味 |
|---|---|---|
| `Flags [S]` | SYN | 接続したい |
| `Flags [S.]` | SYN ＋ ACK（`.` は ACK） | 受け入れる |
| `Flags [.]` | ACK | 受け取った |
| `Flags [P.]` | PUSH ＋ ACK | データを運んでいる |
| `Flags [R.]` | RST ＋ ACK | 断る（そのポートで誰も待ち受けていない） |
| `Flags [F.]` | FIN ＋ ACK | 接続を終える |

UDP と ICMP には接続が無いので、ハンドシェイクも無い。いきなり 1 つ目のパケットで用件を送る。

### Client VM から TCP を送る

`ping` のように「TCP 専用の 1 コマンド」は無いが、TCP を使うプログラムで接続すれば、それが TCP のパケットになる。

```bash
ssh 10.0.0.1                                          # SSH で接続する
nc -zv 10.0.0.1 22                                    # 接続できるかだけ確かめる（netcat が必要）
timeout 1 bash -c '</dev/tcp/10.0.0.1/22' && echo ok  # 何も入れずに bash だけで接続する
```

2026-10-24 に、Router VM で `sudo tcpdump -i ens37 -n -c 3 tcp port 22` を動かしたまま、Client VM で `ssh 10.0.0.1` を実行した。取れたのはハンドシェイクではなく、`10.0.0.1.42784 > 10.0.0.10.22` の `Flags [P.]` だった。これは、MacBook から `ssh debian-client` で Client VM に入っている**多段 SSH の接続**（Router VM が中継している）のパケットである。Client VM のターミナルでのキー入力や画面表示を運んでいる。

ハンドシェイクだけを見るには、多段 SSH の接続を除外して、Router VM の 22 番ポートへの接続だけに絞る。

```bash
sudo tcpdump -i ens37 -n -c 3 '(dst host 10.0.0.1 and dst port 22) or (src host 10.0.0.1 and src port 22)'
```

## 質問37・38：ping にポートは無いが、ソケットは作る

### ソケットとポートは別のもの

| 言葉 | 何か | たとえ |
|---|---|---|
| **ソケット** | プログラムがネットワークで通信するための**窓口**。プログラムが OS に「通信したい」と頼むと作られる | 電話機 |
| **ポート番号** | TCP・UDP のヘッダにある番号。届いたパケットを、**どのソケットに渡すか**を見分けるのに使う | 内線番号 |

### ソケットを作る流れ

```text
① socket()           ソケット（窓口）を作る。何のプロトコルで使うかだけを決める
        ↓
② bind() / connect()  住所を決める（指定しなければ OS が自動で割り当てる）
        ↓
③ send() / recv()     送受信する
```

①の時点では、まだ住所は無い。**どんな住所になるかは、①で選んだプロトコルで決まる。**

| ①で選ぶプロトコル | ②で付く住所 | 例 |
|---|---|---|
| TCP | IP ＋ ポート | `10.0.0.10:42784` |
| UDP | IP ＋ ポート | `10.0.0.10:68` |
| ICMP（ping） | **IP だけ** | `10.0.0.10` |

TCP・UDP の「IP ＋ ポート」の組は、**ソケットアドレス**と呼ばれる。「ソケットを作ると、IP とポートの住所ができる」という理解は、TCP・UDP については正しい。ただし、それは TCP・UDP の場合の話で、「TCP・UDP ではない → ソケットを作らない」とはならない。

### ping のソケット

`ping` コマンドは、ICMP 用のソケットを作って echo request を送る。ポートが無いので、返ってきた echo reply をどの `ping` コマンドに渡すかは、**ICMP の `id` 番号**で見分ける。

2 つのターミナルで同時に `ping` を打っても結果が混ざらないのは、`id` が違うからである。TCP・UDP でポート番号が担っている役割を、ping では `id` が担っている。

> 💡 Linux の `ping` は、`SOCK_DGRAM` の ICMP ソケット（一般ユーザーでも作れる「ping ソケット」）を使うことが多い。環境によっては `SOCK_RAW`（生のパケットを扱うソケット。管理者の権限が必要）を使う。どちらも ICMP を扱うためのソケットの種類である。

## 質問39：ping にサーバーは無い。カーネルが返事をする

```text
Client VM（送る側）                       Router VM（受ける側）
┌────────────────────┐                ┌────────────────────┐
│ ping コマンド        │                │ （プログラムは無い）  │
│   ↓ ソケットを作る    │                │                    │
│ カーネル             │ ─ echo request →│ カーネルが自分で返事 │
│   ↑ id で見分けて渡す │ ← echo reply ── │                    │
└────────────────────┘                └────────────────────┘
```

| | 送る側（Client VM の `ping`） | 受ける側（Router VM） |
|---|---|---|
| ソケット | **作る**（ICMP 用のソケット） | **作らない** |
| ポート番号 | 無い | 無い |
| 返事をするのは | — | **カーネル**が自動で返す |

TCP・UDP との違い：

| | ping（ICMP） | ssh（TCP） |
|---|---|---|
| 送る側のソケット | 作る | 作る |
| 受ける側のソケット | **無い**（カーネルが返事） | **必要**（sshd が 22 番で待ち受け） |
| 受ける側の準備 | 不要。OS が起動していれば返事をする | sshd の起動が必要 |
| 見分ける番号 | `id` | ポート番号 |

ping が疎通確認によく使われるのは、**サービスが動いているかどうかに関係なく、OS とネットワークが生きていれば返事が来る**からである。

### カーネルが返事をしないようにもできる

カーネルが返事をしているので、カーネルの設定やファイアウォールで止められる。

```bash
sudo sysctl -w net.ipv4.icmp_echo_ignore_all=1   # ping に返事をしない（一時的）
```

実務で「サーバーは動いているのに ping が通らない」ときは、たいていファイアウォールで ICMP を止めている。AWS のセキュリティグループも、初期状態では ICMP を許可していない。

### TCP・UDP でも、待ち受けがいないときはカーネルが返事をする

| 送ったもの | 待ち受けがいないときのカーネルの返事 | 送った側に出るエラー |
|---|---|---|
| TCP の SYN | **RST**（`tcpdump` では `Flags [R.]`） | `Connection refused` |
| UDP のパケット | **ICMP の Destination Unreachable（Port Unreachable）** | `Connection refused` など |

UDP の場合、断りの返事に ICMP が使われる。ICMP が「連絡・エラー通知」用のプロトコルだということが、ここでも分かる。

## 質問40・41：ping のソケットは、誰が、いつ作るのか

### ping は ICMP を使い、カーネルが返事をする（質問40）

質問40 の認識は正しい。補足が 2 つある。

- **「OS」は、正確には OS の中の「カーネル」である。** sshd のような「OS の上で動くプログラム」が返事をしているわけではない。カーネルのネットワーク処理が、echo request を受け取ると、その場で echo reply を返す。
- **ping は、ICMP の中の「echo request / echo reply」という種類を使っている。** ICMP にはほかにも「宛先に届かない」「TTL が切れた」などの種類がある（[ICMP は「連絡・エラー通知」用](#icmp-は連絡エラー通知用)）。

ただし、カーネルの設定（`net.ipv4.icmp_echo_ignore_all`）やファイアウォールで止められていると、返事をしない。ping が通らないことが、そのまま「相手が止まっている」という意味にはならない。

### 誰が、いつ作るか（質問41）

| | ソケットを作るのは誰か | いつ作るか | 必要か |
|---|---|---|---|
| ping を**送る側** | **`ping` コマンド**（プログラム）が、カーネルに頼んで作る | `ping` を実行した直後 | **必要** |
| ping を**受ける側** | 誰も作らない | — | **不要**（カーネルの中だけで処理が終わる） |

「作る必要が無い気がする」という感覚は、**受ける側については正しい**。送る側では、TCP・UDP と同じく、プログラムがソケットを作る。

### 送る側：`ping` コマンドもただのプログラム

`ping` は、`ssh` などと同じく、OS の上で動く普通のプログラムである（Debian では `/usr/bin/ping`）。プログラムがネットワークにパケットを送ったり、返事を受け取ったりするには、**カーネルに頼むしかない。その頼む窓口がソケット**である。

`ping -c 1 10.0.0.1` の流れ：

```text
① ping を実行する
② ping がカーネルに「ICMP 用のソケットを作って」と頼む      ← ここで作る
③ ping がソケットに echo request（id・seq 付き）を渡す
④ カーネルが echo request を送り出す
⑤ echo reply が返ってくる → カーネルが id を見て、このソケットに渡す
⑥ ping がソケットから reply を受け取り、time=0.412 ms を計算して表示する
⑦ ping が終わる → ソケットも閉じられる
```

ソケットが必要なのは⑤⑥のためである。返事を受け取って時間を表示するのは `ping` コマンドなので、カーネルから `ping` コマンドへ返事を渡す窓口が要る。

### 受ける側：プログラムが関わらないので要らない

Router VM 側では、echo request を受け取ってから echo reply を返すまで、**すべてカーネルの中で完結する**。返事を渡す先のプログラムがいないので、窓口（ソケット）も要らない。

> 💡 厳密には、Linux のカーネルは ICMP を送るときに、内部の部品としてソケットのような仕組みを使っている。ただし、それはカーネルが起動時から持っている内部用のもので、プログラムが作るソケットとは別物である。`ss` などのコマンドにも出てこない。「プログラムのためのソケットは作らない」と理解しておけば十分である。

### TCP と並べると

| | 送る側（クライアント） | 受ける側（サーバー） |
|---|---|---|
| TCP（ssh） | `ssh` を実行したときに、`ssh` がソケットを作る | **sshd の起動時**に、sshd が待ち受け用のソケットを作る。だから先に起動しておく必要がある |
| ICMP（ping） | `ping` を実行したときに、`ping` がソケットを作る | **作らない**。カーネルが最初から返事をする役を持っている |

「サーバーを先に起動しておく必要がある」というのは、**受ける側で、先に待ち受けのソケットを作っておく必要がある**という意味である。ping では、その役をカーネルが最初から持っているので、準備が要らない。

## 質問42：TCP・UDP は、クライアントもサーバーもソケットを作る

TCP も UDP も、**クライアントとサーバーの両方がソケットを作る**。違いはサーバー側にあり、TCP のサーバーは 2 種類のソケットを使う。

### TCP

```text
サーバー（sshd）                              クライアント（ssh）
① 起動時に「待ち受け用ソケット」を作る（22番）
                                           ② 接続するときにソケットを作る
        ←────── 3ウェイハンドシェイク ──────→
③ 接続ごとに「通信用ソケット」が新しくできる
        ←────── データのやりとり ──────→
```

| | 作るソケット | いつ |
|---|---|---|
| サーバー | **待ち受け用**ソケット（1 つ） | 起動時 |
| サーバー | **通信用**ソケット（クライアント 1 台の接続につき 1 つ） | 接続を受け入れたとき（`accept()`） |
| クライアント | 通信用ソケット（1 つ） | 接続するとき |

待ち受け用のソケットは「受付窓口」で、実際のやりとりは接続ごとの通信用ソケットで行う。3 人が同時に SSH でつないでいれば、sshd 側には待ち受け用 1 つと、通信用 3 つがあることになる。

### UDP

| | 作るソケット | いつ |
|---|---|---|
| サーバー | ソケット（1 つ） | 起動時 |
| クライアント | ソケット（1 つ） | 送る前 |

UDP には接続が無いので、サーバーは **1 つのソケットで全員とやりとりする**。届いたパケットの送信元を見て、誰に返事をするかを決める。

### ping と並べると

| | クライアント（送る側） | サーバー（受ける側） |
|---|---|---|
| TCP | 作る | 作る（待ち受け用 ＋ 接続ごとの通信用） |
| UDP | 作る | 作る（1 つで全員とやりとり） |
| ICMP（ping） | 作る | **作らない**（カーネルが返事） |

## 質問36：ping が通るのに TCP が通らない原因

### ping が通って分かること・分からないこと

| 分かること | 分からないこと |
|---|---|
| 相手まで IP で届き、戻る経路もある | そのポートで、プログラムが待ち受けているか |
| 途中と相手で、ICMP が許可されている | 途中と相手で、TCP のそのポートが許可されているか |
| 相手の OS が動いている | 大きいパケットも届くか |

### 主な原因

| 原因 | 何が起きているか | よくある症状 |
|---|---|---|
| **① 待ち受けているプログラムがいない** | サービスが止まっている、ポート番号が違う | すぐに `Connection refused`（カーネルが RST を返す） |
| **② ファイアウォールが TCP のそのポートを止めている** | 相手（nftables、Windows ファイアウォール）や途中の機器（社内ファイアウォール、AWS のセキュリティグループ）が、ICMP は許可して、そのポートは許可していない | 黙って捨てる設定なら、しばらく待って `Connection timed out`。拒否の返事をする設定なら、すぐ失敗する |
| **③ `127.0.0.1` でしか待ち受けていない** | プログラムが「自分自身からの接続だけ受け付ける」設定になっている | 相手のサーバーの中からはつながるが、外からは `Connection refused` |
| **④ MTU の問題** | ハンドシェイクは成功するが、大きいパケットが途中で捨てられる。ping は小さいパケットなので通る | 接続はできるのに、データの途中で止まる（SSH のログイン後に固まる、など） |
| **⑤ アプリケーション側の問題** | TCP はつながっているが、TLS の証明書や認証で失敗している | 接続後にエラーが出る |

実務でいちばん多いのは①と②である。

### 切り分け方

まず、**エラーの種類**を見る。

| 症状 | 意味 | 疑う場所 |
|---|---|---|
| すぐに `Connection refused` | 相手まで届いたが、そのポートで誰も待ち受けていない | ①③：相手で `ss -lntp` を実行し、待ち受けを確認する |
| 長く待って `Connection timed out` | 途中か相手で、黙って捨てられている | ②：ファイアウォール、セキュリティグループ |
| すぐに `No route to host` など | ファイアウォールが「拒否」の ICMP を返した | ②：拒否しているファイアウォール |
| つながるが途中で止まる | 大きいパケットだけ届かない | ④：`ping -M do -s 1472 <相手>` で、大きい ping が通るか試す |

さらに確かめる道具：

- `nc -zv <相手> <ポート>`：そのポートに TCP でつながるかだけを試す
- 相手で `tcpdump`：SYN が届いているかを見る。届いていなければ途中で止められている。届いていて返事が無ければ、相手の問題

### このラボで再現するなら

Phase 3 で nftables のファイアウォールを作るときに、②を自分で再現できる。

- 捨てる設定（`drop`）にすると、`Connection timed out` になる
- 断る設定（`reject`）にすると、すぐにエラーが返る
- 「ICMP は許可して、22 番だけ止める」設定を作れば、「ping は通るのに TCP は通らない」状態になる

## 質問43：ping が通っても、TCP・UDP が届くとは限らない

質問43 の認識は正しい。ping が通って分かるのは、次の 2 点だけである。

- 相手まで **IP で届き、戻る経路もある**
- 途中と相手で **ICMP が許可されている**

### TCP・UDP が越える 2 つの関門

| 関門 | 引っかかると |
|---|---|
| **ファイアウォール**：途中や相手で、そのプロトコル・ポートが許可されているか | 相手のプログラムまで**届かない**（捨てられるか、拒否される） |
| **待ち受け**：相手で、そのポートを待ち受けているプログラムがいるか | 相手の OS には届くが、**受け取るプログラムがいない**（TCP は RST、UDP は ICMP の Port Unreachable が返る） |

「届かない」には、2 種類ある。

```text
① 途中で止められる         クライアント ──×  ファイアウォール        相手
② OS には届くが渡らない    クライアント ────────────────→ 相手の OS ─×→ （プログラムがいない）
```

### UDP は特に確かめにくい

TCP は、ハンドシェイクの成否で「つながったか」がはっきり分かる。UDP にはハンドシェイクが無いので、返事が来なくても、次のどれなのかを区別できない。

- 途中で捨てられた（届いていない）
- 届いたが、相手が返事をしない仕様だった
- 返事が途中で捨てられた

UDP の疎通を確かめるときは、**そのプロトコル自体で試す**のが確実である。

| UDP のサービス | 確かめ方 |
|---|---|
| DNS（53 番） | `dig @<DNS サーバー> example.com` で答えが返るか |
| DHCP（67 / 68 番） | 実際に IP アドレスをもらえるか（`sudo dhcpcd -U <NIC>` など） |

## まとめ

- **ICMP は TCP とも UDP とも別のプロトコル**である。3 つとも IP の中に入って運ばれ、IP ヘッダのプロトコル番号（ICMP は 1、TCP は 6、UDP は 17）で見分けられる。
- ICMP は、OSI 参照モデルでは **ネットワーク層（第 3 層）**で、IP と同じ層である。形の上では IP の中に入っているが、役割は IP の付属品である。TCP・UDP はトランスポート層（第 4 層）。
- ICMP は、ネットワークの**連絡・エラー通知**用である。`ping`（echo request / reply）のほか、宛先に届かないことや、TTL が切れたことを知らせる。
- **ICMP にはポート番号が無い。** ポートは TCP・UDP のヘッダにある項目である。ping では、ポートの代わりに `id` で見分ける。
- **ping もソケットを作る。** ソケットの住所が「IP ＋ ポート」になるのは TCP・UDP の場合で、ICMP のソケットの住所は IP だけである。
- **ping にはサーバーが無い。** 受ける側では、**OS のカーネルが自分で返事をする**。TCP・UDP は、受ける側でプログラムが待ち受けている必要がある。
- ping のソケットは、**送る側の `ping` コマンドが、実行した直後に**作る。返事を `ping` コマンドに渡す窓口が必要だからである。受ける側はカーネルの中だけで処理が終わるので、作らない。
- **TCP・UDP は、クライアントもサーバーもソケットを作る。** TCP のサーバーは、待ち受け用のソケット 1 つと、接続ごとの通信用のソケットを使う。UDP のサーバーは、1 つのソケットで全員とやりとりする。
- **ping が通っても、TCP・UDP が届くとは限らない。** TCP・UDP には、ファイアウォール（そのポートが許可されているか）と待ち受け（受け取るプログラムがいるか）という関門がある。UDP はハンドシェイクが無いので、そのプロトコル自体（DNS なら `dig` など）で確かめる。
- ping が通るのに TCP が通らないときの主な原因は、待ち受けているプログラムがいないこと（`Connection refused`）と、ファイアウォールが TCP のそのポートを止めていること（`Connection timed out` など）である。
