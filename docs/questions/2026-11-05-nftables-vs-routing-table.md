## 疑問

> **質問66**：Router VM で `nft --version` を打つと、`-bash: nft: command not found` と出た。nftables は入っていないのか？

> **質問67**：`sudo nft list ruleset` を打つと、何も出なかった。これ（nftables のルール）は、ルーティングテーブルのようなものか？

> **質問68（追加質問）**：nftables は「NAT テーブル」と言うのか？

> **質問69（追加質問）**：nftables（の NAT ルール）は出ていくところに置くとのことだが、戻ってくるときもこのテーブルを参照して、ローカルネットワークに流さないといけない気がする。nftables にその機能はあるか？

## 結論

| 質問 | 答え |
|---|---|
| `nft: command not found` は入っていないということ？ | **違う。入っていた。** `nft` は `/usr/sbin/nft` にあり、`/usr/sbin` は一般ユーザーの PATH に無い。`sudo nft --version` で `nftables v1.1.3` と出た |
| nftables のルールはルーティングテーブルのようなもの？ | **似ているが、役割が違う別の表。** ルーティングテーブルは「どこへ渡すか」、nftables は「どう扱うか（通す・捨てる・書き換える）」を決める。両者は協力して動く |
| nftables は NAT テーブルのこと？ | **違う。** nftables は仕組み全体。NAT テーブルは、その中に作る table の1つ。正しい名前は nftables（複数形） |
| 帰りの書き戻しの機能はある？ | **ある。しかも帰り用のルールは書かなくてよい。** 行きで書き換えたときの conntrack の記録を使って、返事の宛先を自動で書き戻す |

## 質問66：`nft: command not found` と出た

```text
kajih@debian-router:~$ nft --version
-bash: nft: command not found
kajih@debian-router:~$ sudo nft --version
nftables v1.1.3 (Commodore Bullmoose #4)
```

- Debian では、`nft` は `/usr/sbin/nft` に置かれる。`/usr/sbin` は管理者用のコマンドの置き場所で、一般ユーザー（`kajih`）の PATH には入っていない。そのため、入っていても `command not found` になる
- `sudo` を付けると `/usr/sbin` も探すので、見つかる
- `nft` は、いつも `sudo` を付けて実行する
- v1.1.3 は、Debian 13（trixie）に入っているバージョン

本当に入っていない場合は、`sudo apt install nftables` で入れる。

## 質問67：nftables のルールはルーティングテーブルのようなものか

`sudo nft list ruleset` で何も出なかったのは、ルールが1つも無いから。今の Router VM は、**何も書き換えず、何も止めずに**転送している。

### 似ているところ

- どちらも Linux カーネルの中にある表で、パケットが通るたびに見られる
- どちらもコマンドで中身を見たり、足したりできる（`ip route` と `nft`）
- どちらも、コマンドで足しただけでは再起動すると消える

### 違うところ：役割

| | ルーティングテーブル | nftables のルール |
|---|---|---|
| 決めること | パケットを**どこへ**渡すか | パケットを**どう扱うか**（通す・捨てる・書き換える） |
| 見え方 | 1行 = 宛先の範囲と渡す相手 | 1行 = 条件と動作（「ens33 から出るなら、送信元を書き換える」など） |
| 選び方 | 当てはまる行のうち、いちばん細かい1行（ロンゲストマッチ） | 上から順に見ていき、条件に合った行の動作を実行する |
| 中身が空のとき | どこにも送れない | 何もしない（全部そのまま通す） |

ルーティングテーブルは「行き先を決める表」、nftables は「**関所**に置くルールの一覧」と考えるとわかりやすい。

### パケットの通り道と関所（フック）

nftables のルールは、パケットが Router VM の中を通る道の途中にある**関所**（フック）に置く。

```text
                                    ┌──→ [input] ──→ Router VM 自身が受け取る
                                    │
 ens37 ──→ [prerouting] ──→ ルーティング判断
 （届く）                           │
                                    └──→ [forward] ──→ [postrouting] ──→ ens33
                                                            ↑              （出ていく）
                                                     ここでマスカレード

 Router VM 自身が送る ──→ [output] ──→ ルーティング判断 ──→ [postrouting] ──→ 出ていく
```

| 関所 | いつ通るか | 主な使い道 |
|---|---|---|
| prerouting | 届いた直後（ルーティング判断の前） | 宛先の書き換え（DNAT、ポート転送） |
| input | Router VM 自身宛てのとき | Router VM を守るファイアウォール |
| forward | 転送するとき | LAN と WAN の間のファイアウォール（labs/05） |
| output | Router VM 自身が送るとき | — |
| postrouting | 出ていく直前（ルーティング判断の後） | **送信元の書き換え（マスカレード）** |

- マスカレードを postrouting に置くのは、出ていく NIC（ens33）がルーティング判断で決まった**後**でないと、「どの IP に書き換えるか」がわからないから
- ルーティングテーブルは、この図の「ルーティング判断」の場所で使われる。nftables は、その前後の関所でパケットを扱う。**両者は別の表で、協力して動いている**

### nftables の入れ物の構造

```text
table（テーブル）  … ルールをまとめる入れ物。例：NAT 用のテーブル
 └─ chain（チェイン） … どの関所に置くか。例：postrouting に置くチェイン
     └─ rule（ルール） … 条件と動作。例：ens33 から出るならマスカレード
```

`sudo nft list ruleset` は、この入れ物をすべて表示するコマンド。今は table が1つも無いので、何も出なかった。

## 質問68：nftables は「NAT テーブル」と言うのか

言わない。名前の範囲が違う。

| 用語 | 何か |
|---|---|
| **nftables** | Linux でパケットを扱う**仕組み全体**（とそのコマンド `nft`）。ファイアウォールも NAT もこれで設定する |
| **NAT テーブル** | nftables の中に作る **table の1つ**。NAT 用のルールをまとめた入れ物 |

```text
nftables（仕組み全体）
 ├─ table：NAT 用      ← これを「NAT テーブル」と呼ぶ
 │   └─ chain：postrouting
 │       └─ rule：ens33 から出るならマスカレード
 └─ table：ファイアウォール用（labs/05 で作る）
     └─ chain：forward
         └─ rule：…
```

- 正しい名前は **nftables**（複数形）。`nftable` という言い方はしない
- 「NAT テーブル」という呼び方は、前の世代の仕組みである **iptables** から来ている。iptables には `filter`・`nat` などの決まったテーブルが最初から用意されていた。nftables では table を自分で作り、名前も自由に付ける。習慣で `nat` と名付けることが多いので、今でも「NAT テーブル」と呼ばれる

## 質問69：戻ってくるときの書き戻しは、nftables にあるか

ある。しかも、**帰り用のルールを自分で書く必要はない。** conntrack（コネクショントラッキング）が自動でやる。

### 仕組み

NAT のルールが見られるのは、**通信の最初のパケットだけ**。

1. **最初のパケット（行き）**：postrouting の NAT ルールに当てはまり、送信元を `192.168.22.129` に書き換える。このとき conntrack に「`10.0.0.10` ⇔ `8.8.8.8` の通信を、`192.168.22.129` に書き換えた」と記録する
2. **返事（帰り）**：ens33 に届いたら、**ルーティング判断の前**（prerouting の場所）で conntrack の記録と照らし合わせる。この通信の返事だとわかれば、宛先を `10.0.0.10` に書き戻す。NAT ルールは見ない
3. **2つ目以降のパケット（行き）**：NAT ルールは見ずに、conntrack の記録どおりに書き換える

```text
【行き（最初のパケット）】
 ens37 ──→ ルーティング判断 ──→ [postrouting] ──→ ens33
                                    │
                             NAT ルールに当てはまる
                             → src を 192.168.22.129 に書き換え
                             → conntrack に記録 ─────────┐
                                                          │
【帰り】                                                   │
 ens37 ←── [forward] ←── ルーティング判断 ←── [prerouting] ←── ens33
                              │                  │
                    宛先 10.0.0.10 なので     conntrack の記録を見て ←┘
                    ens37 の行が選ばれる      dst を 10.0.0.10 に書き戻す
```

### 書き戻しがルーティング判断の前である理由

帰りの返事は、届いた時点では宛先が `192.168.22.129`（Router VM 自身）。このままルーティング判断をすると、「自分宛て」として Router VM 自身が受け取ってしまう。

ルーティング判断の**前に**宛先を `10.0.0.10` に書き戻すことで、ルーティングテーブルの `10.0.0.0/24 dev ens37` の行が選ばれ、Client VM へ転送される。

| | 書き換えのタイミング | 理由 |
|---|---|---|
| 行き | ルーティング判断の**後**（postrouting） | 出ていく NIC が決まらないと、どの IP に書き換えるかわからない |
| 帰り | ルーティング判断の**前**（prerouting） | 先に宛先を戻さないと、Router VM 自身宛てと判断されてしまう |

### まとめ

- 自分で書くのは「**行き**のルール1つ」だけ
- 帰りの書き戻しは、conntrack の記録を使って自動で行われる
- `conntrack -L` で、この記録を実際に見られる（NAT を設定した後に試す）
