## 疑問

> **質問1**：そもそも `ip route` コマンドは何をするものなのか？ルーティングテーブルにアドレスを加えるもの？

> **質問2**：ルーティングテーブルとは何か？どのような情報が格納される？永続化されるもの？それとも一時的なファイル？

> **質問3（追加質問）**：`ip route` で表示されたルーティングテーブルはメモリ上にあり、再起動で消えるとのことだが、永続化はしないのか？

## 結論

| 質問 | 答え |
|---|---|
| `ip route` は何をする？ | ルーティングテーブルを**見る・変える**コマンド。引数なしの `ip route` は**表示するだけ**で、何も変えない |
| アドレスを加えるもの？ | **半分正解。** 加えられるのは `ip route add` のときだけ。しかも加えるのは**アドレスではなく経路**（「この宛先へはこう送る」というルール 1 行）。アドレスを加えるのは `ip addr add` |
| ルーティングテーブルとは？ | **「この宛先には、こう送る」というルールの一覧表**。パケットを送るたびにカーネルが参照する |
| どんな情報が入っている？ | 1 行ごとに、宛先の範囲・次に渡す相手（`via`）・出ていく NIC（`dev`）など |
| 永続化される？ファイル？ | **どちらでもない。** ファイルではなく**カーネルのメモリ上**にあり、再起動で消える。再起動後も同じ行があるのは、設定ファイルなどから**起動のたびに作り直されている**から |
| 永続化はしないのか？ | **テーブルそのものは保存しない。保存するのは、テーブルを作るための設定**（`/etc/network/interfaces` など）。起動のたびに設定から作り直すので、結果として再起動後も同じ表になる |

## 質問1：`ip route` コマンドは何をするものか

### `ip` コマンドの仲間

`ip` は `ip <対象> <動作>` の形で使う。対象によって扱うものが違う。

| コマンド | 扱うもの | このラボでの例 |
|---|---|---|
| `ip link` | NIC そのもの（UP / DOWN、MAC アドレス） | ens33 が UP になっているか |
| `ip addr` | NIC に付ける IP アドレス | `10.0.0.10/24` |
| `ip route` | ルーティングテーブル（経路） | `default via 10.0.0.1 dev ens33` |
| `ip neigh` | 同じネットワークにいる相手の IP と MAC の対応 | `10.0.0.1` の MAC アドレス |

`ip addr` と `ip route` は扱うものが別である。だから `ip addr` にはデフォルトゲートウェイが出ない（[前回の疑問](2026-10-11-ip-addr-and-default-gateway.md)）。

### `ip route` の動作

| コマンド | すること | `sudo` |
|---|---|---|
| `ip route`（= `ip route show`） | 表を**表示する** | 不要 |
| `ip route get <宛先>` | その宛先ならどう送るかを**問い合わせる**（実際には送らない） | 不要 |
| `sudo ip route add <経路>` | 行を**追加する** | 必要 |
| `sudo ip route del <経路>` | 行を**削除する** | 必要 |
| `sudo ip route replace <経路>` | 行を**置き換える**（無ければ追加する） | 必要 |

普段いちばん使うのは、表示するだけの `ip route` である。

### 「アドレスを加える」ではなく「経路を加える」

labs/01 で実行した次のコマンドを分解する。

```bash
sudo ip route add default via 10.0.0.1 dev ens33
```

| 部分 | 意味 |
|---|---|
| `default` | どの宛先に使う行か（ここでは「ほかに当てはまる行が無い、すべての宛先」） |
| `via 10.0.0.1` | 誰に渡すか（ゲートウェイ） |
| `dev ens33` | どの NIC から出すか |

一文に訳すと：

> ほかに当てはまる行が無い宛先は、**ens33 から出して、10.0.0.1 に渡す**。

加えたのは**送り方のルール 1 行**である。自分の IP アドレスは何も増えていない。

| | `sudo ip addr add 10.0.0.10/24 dev ens33` | `sudo ip route add default via 10.0.0.1` |
|---|---|---|
| 変えるもの | NIC に付いている IP アドレス | ルーティングテーブル |
| 会社でたとえると | 自分の席に名札（住所）を付ける | 「社外宛ての書類は発送窓口へ」というルールを書き足す |

## 質問2：ルーティングテーブルとは何か

### ひとことで

**「この宛先には、こう送る」というルールの一覧表**である。

カーネルがメモリ上に持っていて、パケットを送るたびに参照する。ルーターとして他の機器のパケットを転送するときも、この表で転送先を決める。

```text
送りたいパケット（宛先 8.8.8.8）
        │
        ▼
ルーティングテーブルで宛先を照らし合わせる
        │
        ▼
「ens33 から出して 10.0.0.1 に渡す」と決まる
        │
        ▼
送信
```

### 中身の例（Client VM）

```text
default via 10.0.0.1 dev ens33
10.0.0.0/24 dev ens33 proto kernel scope link src 10.0.0.10
```

**1 行が 1 つのルール**である。

### 1 行に入っている情報

| 表示 | 意味 | 例 |
|---|---|---|
| 先頭 | **宛先**（どの宛先に使う行か） | `default`、`10.0.0.0/24` |
| `via` | **次に渡す相手**（ゲートウェイ）。この表示が無い行は、相手に直接届ける | `via 10.0.0.1` |
| `dev` | **出ていく NIC** | `dev ens33` |
| `src` | 送信元として使う自分の IP | `src 10.0.0.10` |
| `proto` | 誰がこの行を作ったか。`kernel` はカーネルが自動で作った行。`proto` が表示されない行は、`ip route add` や `gateway` 行で追加した行 | `proto kernel` |
| `scope` | 宛先までの距離。`link` は「同じネットワーク内で、直接届く」 | `scope link` |
| `metric` | 同じ宛先の行が複数あるときの優先度。小さいほうが優先 | `metric 100` |

最初の 3 つ（宛先・`via`・`dev`）を読めれば十分である。

> 💡 `ip route` が表示しているのは `main` という名前の表である。実は自分自身の IP 宛てなどを扱う別の表もあるが、今は `main` だけ見ればよい。

### どの行が使われるか

宛先 IP を各行と照らし合わせて、**当てはまる行のうち、範囲が一番狭い行**を使う。`/` の後ろの数字が大きいほど、範囲は狭い。**行の並び順は関係ない。**

| 宛先 | 当てはまる行 | 使われる行 |
|---|---|---|
| `10.0.0.1` | `10.0.0.0/24` と `default` | `10.0.0.0/24`（`/24` のほうが狭い） |
| `8.8.8.8` | `default` だけ | `default` |

`default` は `0.0.0.0/0`、つまり**すべての宛先に当てはまる、一番広い範囲**である。そのため、ほかに当てはまる行が無いときにだけ使われる。

> 💡 住所でたとえると、宛先が「東京都」の行と「東京都千代田区」の行の両方に当てはまるなら、より細かい「東京都千代田区」の行を使う。

### Router VM の表

Router VM は NIC が 2 つあるので、自分のネットワークの行も 2 つある（2026-10-11 の実行結果）。

```text
kajih@debian-router:~$ ip route
default via 192.168.22.2 dev ens33 proto dhcp src 192.168.22.129 metric 1002
10.0.0.0/24 dev ens37 proto kernel scope link src 10.0.0.1
192.168.22.0/24 dev ens33 proto dhcp scope link src 192.168.22.129 metric 1002
```

| 宛先 | 使われる行 | 動き |
|---|---|---|
| `10.0.0.10`（Client VM） | `10.0.0.0/24` | ens37（LAN 側）から直接届ける |
| `192.168.22.2`（VMware NAT） | `192.168.22.0/24` | ens33（WAN 側）から直接届ける |
| `8.8.8.8` | `default` | ens33 から出して `192.168.22.2` に渡す |

ens33 側の 2 行は、DHCP クライアント（dhcpcd）が作った行なので `proto dhcp` が付いている。`metric 1002` は dhcpcd が付ける優先度（1000 ＋ インターフェース番号 `2`）。`default` は 1 行しかないので、今は影響しない。

labs/02 で IP フォワーディングを有効にすると、Router VM は Client VM から来たパケットも、この表を使って転送先を決めるようになる。

## 永続化されるのか

**されない。ファイルでもない。**

| | ルーティングテーブル |
|---|---|
| ある場所 | カーネルのメモリ上 |
| 再起動すると | **消える** |
| 変え方 | `ip route add` / `del` など（すぐ反映されるが、一時的） |

それでも再起動後に `default via 10.0.0.1` があるのは、**起動のたびに作り直されている**からである（[persistent-config.md](../concepts/persistent-config.md) と同じ考え方）。

```text
[ディスク] /etc/network/interfaces（再起動しても残る）
    address 10.0.0.10/24  ─┐
    gateway 10.0.0.1      ─┤ 起動するたびに読み込まれる
                           ▼
[メモリ] ルーティングテーブル（再起動で消える）
    10.0.0.0/24 dev ens33 proto kernel scope link src 10.0.0.10
    default via 10.0.0.1 dev ens33
                           ▲
    sudo ip route add ... ─┘ 手で足した行（次の起動では作られない）
```

### 各行は誰が作っているか

| 行 | 誰が作るか | 再起動後 |
|---|---|---|
| `10.0.0.0/24 ... proto kernel`（Client VM） | IP アドレスが付くと、カーネルが自動で作る（アドレスは設定ファイルの `address` から） | 作り直される |
| `default via 10.0.0.1`（Client VM） | `ifup` が設定ファイルの `gateway` 行から作る | 作り直される |
| `default via 192.168.22.2`（Router VM） | DHCP クライアントが、DHCP で受け取った情報から作る | 作り直される |
| 手で `sudo ip route add` した行 | 自分 | **消える** |

### 手で足した行を残したいとき

設定ファイルの `iface` の段落に、`up` で始まる行として書く。インターフェースが起動するたびに、そのコマンドが実行される。

```text
iface ens33 inet static
    address 10.0.0.10/24
    gateway 10.0.0.1
    up ip route add 192.168.100.0/24 via 10.0.0.1
```

※ 書き方の例である。このラボではまだ必要ない。

> 💡 `/proc/net/route` を `cat` すると、ルーティングテーブルがファイルのように読める。ただしこれは、読むたびにカーネルがメモリの中身を書き出している**窓口**であり、ディスクには保存されていない。中身は 16 進数で読みにくいので、普段は `ip route` を使う。

## 質問3：ルーティングテーブルは永続化しないのか

### ひとことで

**テーブルそのものは保存しない。保存するのは、テーブルを作るための「設定」のほうである。**

起動のたびに、その設定からテーブルを作り直す。だから結果として、再起動しても同じ表になる。永続化の仕組みが「表を保存する」ではなく「**設定から毎回作り直す**」になっている、ということである。

```text
設定ファイル（ディスク上・再起動しても残る）
        │
        │ 起動するたびに読む
        ▼
ifup / dhcpcd / カーネル
        │
        │ 行を作る
        ▼
ルーティングテーブル（メモリ上・再起動で消える）
```

> 💡 料理でたとえると、保存しておくのは**レシピ**（設定ファイル）である。**できた料理**（ルーティングテーブル）を冷凍しておくわけではなく、毎回レシピから作り直している。

### Router VM で確かめる

Router VM の `/etc/network/interfaces`（[configs/network/debian-router.interfaces](../../configs/network/debian-router.interfaces)）には、**経路の行が 1 つも書かれていない**。それでも、起動するたびに 3 行のテーブルができる。

| テーブルの行 | 元になった設定 | 作ったもの |
|---|---|---|
| `default via 192.168.22.2 dev ens33 proto dhcp ...` | `iface ens33 inet dhcp` | dhcpcd（DHCP サーバーから受け取った情報で作る） |
| `10.0.0.0/24 dev ens37 proto kernel ...` | `iface ens37 inet static` の `address 10.0.0.1/24` | カーネル（アドレスが付くと自動で作る） |
| `192.168.22.0/24 dev ens33 proto dhcp ...` | `iface ens33 inet dhcp` | dhcpcd |

### なぜテーブルそのものを保存しないのか

**理由 1：テーブルの行は、ほかの設定から決まる「結果」だから**

`10.0.0.0/24 dev ens37` の行は、ens37 に `10.0.0.1/24` を付けた結果としてできる。

テーブルも別に保存すると、同じことを 2 か所で管理することになる。たとえば、設定ファイルのアドレスを `10.0.1.1/24` に変えたのに、保存したテーブルには古い `10.0.0.0/24` の行が残る、という食い違いが起きる。

**理由 2：その時の状況で、正しい中身が変わるから**

| 状況 | 起きること |
|---|---|
| DHCP | 配られるアドレスやゲートウェイは、DHCP サーバーしだい。毎回聞いて、その時の答えで作るほうが確実 |
| NIC を DOWN にした | その NIC を使う行は、カーネルが表から消す。使えない NIC への行を残しても意味がない |

つまりルーティングテーブルは、**「今こうなっている」という状態**を表したものである。

| | 設定 | 状態 |
|---|---|---|
| 例 | `/etc/network/interfaces` | ルーティングテーブル |
| 意味 | 「こうしたい」という指示 | 「今こうなっている」という結果 |
| 置き場所 | ディスク（再起動しても残る） | メモリ（再起動で消える） |
| 起動時 | 読み込まれる | 設定から作られる |

自分で足した経路を残したいときも、テーブルではなく**設定ファイルに書く**（[手で足した行を残したいとき](#手で足した行を残したいとき)）。

> 💡 `ip route save` / `ip route restore` で、テーブルそのものを保存して戻すこともできる。ただし、Debian の起動の仕組みでは使われていない。普段は設定ファイルに書けばよい。

## まとめ

- `ip route` は**ルーティングテーブルを見る・変える**コマンド。引数なしなら**表示するだけ**。
- `ip route add` で加えるのは**アドレスではなく経路**（「この宛先へは、この NIC から、この相手に渡す」というルール）。
- ルーティングテーブルは、**宛先ごとの送り方の一覧表**。当てはまる行のうち**一番範囲が狭い行**が使われ、`default` は最後の手段。
- ルーティングテーブルは**カーネルのメモリ上**にあり、ファイルではない。再起動で消えるが、**設定ファイルや DHCP から起動のたびに作り直される**。
- テーブルそのものは保存しない。**保存するのは設定（レシピ）**で、表は毎回そこから作り直す。こうすると設定と表が食い違わず、DHCP などのその時の状況も反映できる。
