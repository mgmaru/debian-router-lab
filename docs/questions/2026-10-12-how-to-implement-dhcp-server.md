## 疑問

> **質問12（追加質問）**：DHCP サーバーの実装は、Web サーバーなどと同じように、ソケットを作って特定のポートでデータを待ち受ける（Listen）感じなのか？ また、プロトコルは ARP か？ 大まかな実装方法を知りたい。

## 結論

| 質問 | 答え |
|---|---|
| ソケットを作って待ち受けるのか？ | **基本は同じ。** ただし TCP ではなく **UDP**（サーバーは 67 番、クライアントは 68 番）を使い、「接続」はない。1 通受け取って 1 通返す、を繰り返す。Web サーバーとの最大の違いは、**相手がまだ IP アドレスを持っていない**ことである |
| プロトコルは ARP か？ | **違う。** DHCP は UDP の上で動く独自のプロトコル（RFC 2131）。ARP は IP を使わない、別の層のプロトコルである。ただし、DHCP の前後では ARP がよく使われる |
| 大まかな実装方法は？ | 「**受け取る → 読み解く → リースの状態を見て決める → 記録する → 返事を組み立てて送る**」のループ。難しいのは、①ネットワークまわり（ブロードキャスト、どの NIC から来たか、IP の無い相手への返信）と、②リース（貸し出し記録）の管理の 2 つ |

## 1. Web サーバーとの比較

### 共通点

| | Web サーバー | DHCP サーバー |
|---|---|---|
| 正体 | 普通のプログラム（ユーザー空間） | 普通のプログラム（ユーザー空間） |
| 待ち受け方 | ソケットを作り、決まったポートで待つ | ソケットを作り、決まったポートで待つ |
| 仕事 | 要求を読んで、返事を返す | 要求を読んで、返事を返す |

ここまでは同じである。DHCP サーバーも、カーネルの機能ではなく、Web サーバーと同じ「問い合わせに答えるプログラム」である（[質問9](2026-10-11-dhcp-role-and-placement.md#質問9dhcp-はルーターの機能か)）。

### 違い 1：TCP ではなく UDP を使う

| | Web サーバー（TCP） | DHCP サーバー（UDP） |
|---|---|---|
| ポート | 80 / 443 | **67**（サーバー）、**68**（クライアント） |
| 接続 | 最初に「接続」を作る（3 ウェイハンドシェイク） | **接続しない**。1 通ずつ独立して送る |
| 待ち受けの手順 | 番号を決める（bind）→ 待機を始める（listen）→ 接続を受け付ける（accept） | 番号を決める（bind）したら、あとは 1 通ずつ受け取るだけ |
| 返事 | 作った接続に書き込む | 毎回、宛先を指定して送る |

**なぜ UDP なのか：** TCP の接続を作るには、両方が IP アドレスを持っている必要がある。DHCP のクライアントは、まだ IP アドレスを持っていない。しかも最初の呼びかけはブロードキャストで、TCP はブロードキャストでは使えない。そのため、接続のいらない UDP が使われる。

### 違い 2：相手がまだ IP アドレスを持っていない

最初に届く DISCOVER は、次のようなパケットである。

```text
Ethernet：送信元 = クライアントの MAC   宛先 = ff:ff:ff:ff:ff:ff（全員）
IP      ：送信元 = 0.0.0.0             宛先 = 255.255.255.255（全員）
UDP     ：送信元ポート = 68            宛先ポート = 67
```

ここから、Web サーバーには無い問題がいくつも出てくる。

| 問題 | 起きること | どう扱うか |
|---|---|---|
| 要求がブロードキャストで届く | 特定の IP（`10.0.0.1`）だけで待ち受けると、`255.255.255.255` 宛てのパケットを受け取れない | 「すべてのアドレス（`0.0.0.0`）」の 67 番で待ち受ける |
| 送信元が `0.0.0.0` | 送信元 IP を見ても、誰からの要求か分からない | DHCP のメッセージの中にある **クライアントの MAC（`chaddr`）** で相手を見分ける |
| 返事を普通に送れない | IP 宛てに普通に送ると、カーネルが相手の MAC を ARP で調べようとする。相手はまだその IP を持っていないので答えない | 返し方を工夫する（次の表） |

**返事の返し方は 3 通りある。**

| 返し方 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| **ブロードキャストで返す** | `255.255.255.255` の 68 番宛てに送る | **いちばん簡単**。普通の UDP ソケットだけでできる | LAN の全員に届く |
| 近隣テーブルに先に書き込む（dnsmasq の方式） | 「配る IP ↔ クライアントの MAC」の対応を近隣テーブルに登録してから、配る IP 宛てに送る | 相手にだけ届く | 近隣テーブルを書き換える処理と権限が必要 |
| 生ソケットで組み立てる（ISC DHCP の方式） | Ethernet・IP・UDP のヘッダーを全部自分で組み立てて送る | 何でもできる | 実装が大変 |

RFC 2131 では、相手に直接届けられない場合はブロードキャストで送ってよいとされている。**最初の実装は、ブロードキャストで十分である。**

### 違い 3：どの NIC から届いたかが大事

Web サーバーは、どの NIC から接続が来たかをあまり気にしない。DHCP サーバーは、**どの NIC（どのネットワーク）から届いたか**で、配る内容が変わる。

- ens37（`10.0.0.0/24`）から届いた → `10.0.0.x` を配り、ゲートウェイは `10.0.0.1`
- ens33（VMnet8）から届いた → **答えてはいけない**（VMware の DHCP サーバーと取り合いになる。[質問11](2026-10-11-dhcp-role-and-placement.md#質問11理解の確認とdhcp-サーバーの台数)）

方法は 2 つある。

| 方法 | 考え方 |
|---|---|
| ソケットを NIC に縛る（`SO_BINDTODEVICE`） | ens37 専用のソケットにする。LAN が 1 つなら、これがいちばん分かりやすい |
| 届いたパケットごとに NIC を教えてもらう（`IP_PKTINFO`） | ソケットは 1 つのまま、受け取るたびに「どの NIC から来たか」を受け取る。LAN が複数あるときに向いている |

### 違い 4：特別な権限が要る

1024 番より小さいポートで待ち受けるには、root 権限（または対応する capability）が必要である。67 番もこれに当たる。

**起動時だけ root で準備をして、その後は権限を落とす**のが定石である。dnsmasq もそうしている。ルーターは外からの攻撃を受けやすい場所なので、ここは意識しておきたい。

## 2. プロトコルは ARP か

### DHCP と ARP は、層が違う

| 層 | DHCP | Web | ARP |
|---|---|---|---|
| アプリケーション | **DHCP**（RFC 2131） | HTTP | — |
| トランスポート | UDP 67 / 68 | TCP 80 / 443 | — |
| ネットワーク | IP | IP | — |
| リンク | Ethernet | Ethernet | **ARP**（Ethernet の上で直接動く） |

| | ARP | DHCP |
|---|---|---|
| 目的 | IP アドレスから MAC アドレスを調べる | 機器に IP アドレスなどの設定を配る |
| 乗っているもの | Ethernet に直接 | UDP（IP の上） |
| Linux での実体 | カーネル（[近隣テーブル](../concepts/neighbor.md)） | ユーザー空間のプログラム |
| 確認するコマンド | `ip neigh` | `dhcpcd -U`（クライアント側） |

### それでも、DHCP のまわりでは ARP がよく登場する

| 場面 | 誰が | 何をするか |
|---|---|---|
| 配る前の確認 | サーバー | 配ろうとしている IP に `ping` して、誰も使っていないか確かめる（dnsmasq は標準でこれをする）。`ping` を送るときに ARP も流れる |
| 使う前の確認 | クライアント | もらった IP を使う前に、ARP で「この IP を使っている人はいる？」と確かめる（RFC 5227）。誰かが使っていたら、サーバーに DECLINE を送る |
| 直接返すとき | サーバー | 近隣テーブルに相手の MAC を書き込んでから返す（上の dnsmasq の方式） |

`tcpdump` で見ると DHCP の前後に ARP が流れるので、混同しやすい。**ARP は DHCP の部品ではなく、まわりで使われる別の仕組み**である。

> 💡 `tcpdump` で DHCP が `BOOTP/DHCP` と表示されるのは、DHCP が **BOOTP**（RFC 951）という古いプロトコルを拡張して作られたからである。メッセージの形もポート番号（67 / 68）も、BOOTP から受け継いでいる。

## 3. メッセージの形

### 全体の重なり

```text
┌ Ethernet ヘッダー（MAC アドレス）
│ ┌ IP ヘッダー（IP アドレス）
│ │ ┌ UDP ヘッダー（ポート 67 / 68）
│ │ │ ┌ DHCP メッセージ
│ │ │ │   固定部分（236 バイト）
│ │ │ │   マジッククッキー（4 バイト）
│ │ │ │   オプション（可変長）
```

DHCP サーバーのプログラムが自分で読み書きするのは、いちばん内側の **DHCP メッセージ**だけである（ブロードキャストで返す場合）。外側のヘッダーは、カーネルが付けてくれる。

### 固定部分

| 欄 | 大きさ | 意味 |
|---|---|---|
| `op` | 1 | `1` = クライアントからの要求、`2` = サーバーからの返事 |
| `htype` / `hlen` | 1 / 1 | ハードウェアの種類と、アドレスの長さ。Ethernet なら `1` / `6`（MAC は 6 バイト） |
| `hops` | 1 | DHCP リレーを何回通ったか |
| `xid` | 4 | **やりとりの番号**。クライアントが決める乱数で、サーバーは同じ値を返事に入れる。どの要求への返事かを対応させるため |
| `secs` | 2 | クライアントが取得を始めてからの秒数 |
| `flags` | 2 | 先頭の 1 ビットが「**返事はブロードキャストで送って**」の印 |
| `ciaddr` | 4 | クライアントが今持っている IP（最初は `0.0.0.0`） |
| `yiaddr` | 4 | **サーバーが配る IP**（your IP address） |
| `siaddr` | 4 | ネットワークブートで使う次のサーバー（普段は使わない） |
| `giaddr` | 4 | DHCP リレーの IP（リレーを通っていなければ `0.0.0.0`） |
| `chaddr` | 16 | **クライアントの MAC アドレス**（先頭 6 バイトを使う） |
| `sname` / `file` | 64 / 128 | ネットワークブート用（普段は使わない） |

### マジッククッキーとオプション

固定部分の直後に、`99.130.83.99` という決まった 4 バイト（マジッククッキー）が来る。「ここから先は DHCP のオプションです」という目印である。

オプションは、**「番号・長さ・値」の 3 つ組**を並べたものである。

```text
例：ゲートウェイ（オプション 3）が 192.168.22.2 のとき
  番号 = 3   長さ = 4   値 = 192.168.22.2（4 バイト）

例：メッセージ種別（オプション 53）が Ack のとき
  番号 = 53  長さ = 1   値 = 5
```

最後に `255`（終わりの印）を置く。読むときは、「番号を読む → 長さを読む → その長さだけ値を読む」を、`255` が来るまで繰り返せばよい。

### 主なオプション

[質問8](2026-10-11-where-to-find-dhcp-server-address.md#出力の読み方) で見た `dhcpcd -U` の項目は、ここから来ている。

| 番号 | 中身 | 誰が入れるか | `dhcpcd -U` での名前 |
|---|---|---|---|
| 53 | **メッセージ種別**（下の表） | 両方（必須） | `dhcp_message_type` |
| 54 | DHCP サーバーのアドレス | サーバー | `dhcp_server_identifier` |
| 50 | クライアントが希望する IP | クライアント | — |
| 55 | クライアントが欲しい設定の一覧 | クライアント | — |
| 61 | クライアントの ID | クライアント | — |
| 12 | ホスト名 | クライアント | — |
| 1 | サブネットマスク | サーバー | `subnet_mask` |
| 3 | ゲートウェイ | サーバー | `routers` |
| 6 | DNS サーバー | サーバー | `domain_name_servers` |
| 15 | ドメイン名 | サーバー | `domain_name` |
| 28 | ブロードキャストアドレス | サーバー | `broadcast_address` |
| 51 | リース時間 | サーバー | `dhcp_lease_time` |
| 58 / 59 | 延長・再取得のタイミング | サーバー | `dhcp_renewal_time` / `dhcp_rebinding_time` |
| 255 | 終わりの印 | 両方 | — |

### メッセージ種別（オプション 53）

| 値 | 名前 | 向き | 意味 |
|---|---|---|---|
| 1 | DISCOVER | クライアント → 全員 | 「誰か IP をください」 |
| 2 | OFFER | サーバー → クライアント | 「この IP はどう？」 |
| 3 | REQUEST | クライアント → サーバー | 「その IP をください」（延長のときもこれ） |
| 4 | DECLINE | クライアント → サーバー | 「その IP は誰かが使っていた」 |
| 5 | ACK | サーバー → クライアント | 「どうぞ」 |
| 6 | NAK | サーバー → クライアント | 「だめです。最初からやり直して」 |
| 7 | RELEASE | クライアント → サーバー | 「IP を返します」 |
| 8 | INFORM | クライアント → サーバー | 「IP は自分で持っているので、ほかの設定だけください」 |

## 4. サーバーの動き：メッセージごとの処理

### DISCOVER が来たら：配る IP を選んで OFFER

**どの IP を選ぶか**は、次の優先順で考える（RFC 2131 の考え方）。

1. その機器向けに**予約**してある IP（MAC ごとに固定で決めたもの）
2. その機器に**今貸している** IP、または前に貸していた IP（同じ機器には、できるだけ同じ IP を配る）
3. クライアントが**希望した** IP（オプション 50）。空いていて、範囲内なら
4. **空いている IP** を、プールから 1 つ

選んだら、（必要なら `ping` で使われていないことを確かめて）その IP を**仮押さえ**する。まだ貸し出しは確定していない。

返す OFFER には、`yiaddr` に選んだ IP、オプションにサブネットマスク・ゲートウェイ・DNS・リース時間・自分のアドレス（オプション 54）を入れる。`xid` はクライアントから来た値をそのまま入れる。

### REQUEST が来たら：4 つの場面を見分ける

REQUEST は、いろいろな場面で送られてくる。**どの場面かは、中身で見分ける。**

| 場面 | いつ | オプション 54（サーバー） | オプション 50（希望 IP） | `ciaddr` | 届き方 |
|---|---|---|---|---|---|
| **選択**（SELECTING） | OFFER を受け取った直後 | **ある** | ある | `0.0.0.0` | ブロードキャスト |
| **再起動**（INIT-REBOOT） | クライアントが再起動して、前の IP を使いたいとき | 無い | ある | `0.0.0.0` | ブロードキャスト |
| **延長**（RENEWING） | リースの半分が過ぎたとき | 無い | 無い | **今の IP** | サーバーへ直接 |
| **再取得**（REBINDING） | 延長できないまま、リースの 87.5% が過ぎたとき | 無い | 無い | **今の IP** | ブロードキャスト |

| 場面 | サーバーがすること |
|---|---|
| 選択 | オプション 54 が**自分なら**：その IP がまだ仮押さえのままか確かめ、**貸し出しを確定して記録**し、ACK。**自分でなければ**：クライアントは別のサーバーを選んだので、仮押さえを解除する（返事はしない） |
| 再起動 | 希望の IP が、このネットワークで正しいか確かめる。正しくて貸してよければ ACK。別のネットワークの IP なら NAK（「やり直して」）。記録が無く、判断できなければ黙る |
| 延長 / 再取得 | その機器に貸している IP なら、期限を延ばして記録し、ACK。知らない貸し出しなら NAK か、黙る |

リースの時間の流れは、次のようになる（[質問8](2026-10-11-where-to-find-dhcp-server-address.md) の Router VM の値）。

```text
0 秒        ACK を受け取る。IP を使い始める
  │
900 秒      （50%）   延長：もらったサーバーに直接 REQUEST
  │
1575 秒     （87.5%） 再取得：全員に REQUEST（どのサーバーでもよいので延ばして）
  │
1800 秒     （100%）  期限切れ：IP を使うのをやめて、DISCOVER からやり直す
```

`dhcpcd -U` で `reason=RENEW` と出ていたのは、900 秒の延長が成功していた、ということである。

### そのほかのメッセージ

| 届いたもの | サーバーがすること |
|---|---|
| DECLINE | その IP は誰かが勝手に使っている。**しばらく配らないように印を付ける**（管理者に知らせるのが望ましい） |
| RELEASE | その IP の貸し出しを終わりにして、空きに戻す |
| INFORM | IP は配らない。DNS などの設定だけを ACK で返す（リース時間は入れない） |

## 5. サーバーが持つ状態：プールとリース

DHCP サーバーの中心は、ネットワークの処理よりも、**「どの IP を、誰に、いつまで貸しているか」の管理**である。

### アドレスプール（設定）

**どの範囲の IP を配るか**を決めておく。

| 項目 | このラボで考えるなら |
|---|---|
| 配る範囲 | 例：`10.0.0.100`〜`10.0.0.199` |
| 範囲に入れてはいけないもの | Router VM 自身（`10.0.0.1`）、静的 IP の機器（Client VM の今の `10.0.0.10`）、ネットワークのアドレス（`.0`）、ブロードキャスト（`.255`） |
| 一緒に配る設定 | サブネットマスク `/24`、ゲートウェイ `10.0.0.1`、DNS、リース時間 |
| 予約 | 「この MAC には、いつもこの IP」という固定の割り当て |

> ⚠️ 静的 IP の機器と配る範囲が重なると、同じ IP が 2 台に付いてしまう。**静的に使うアドレスは、プールの外に置く**のが基本である。

### リース（貸し出し記録）

1 件の貸し出しごとに、次のことを覚えておく。

| 項目 | 意味 |
|---|---|
| クライアントの識別子 | 誰に貸したか。オプション 61（クライアント ID）があればそれ、無ければ MAC（`chaddr`） |
| IP アドレス | 何を貸したか |
| 期限 | いつまで貸しているか |
| 状態 | 下の図 |
| ホスト名 | オプション 12 で送られてきた名前（あれば） |

> 💡 dhcpcd など一部のクライアントは、MAC ではなく独自の ID（オプション 61）で名乗ることがある。「同じ機器には同じ IP」を実現するには、クライアントの見分け方を決めておく必要がある。

**1 つの IP の状態は、次のように移り変わる。**

```text
空き
  │ DISCOVER に対して OFFER した
  ▼
仮押さえ ──（しばらく REQUEST が来ない）──▶ 空き
  │ REQUEST が来て、ACK した
  ▼
貸し出し中 ──（延長の REQUEST）──▶ 貸し出し中（期限が延びる）
  │ 期限切れ、または RELEASE
  ▼
空き

（DECLINE が来たら）→ 使用禁止（しばらくしたら空きに戻す）
```

### リースは永続化する

[ルーティングテーブル](2026-10-11-what-is-ip-route-and-routing-table.md#質問3ルーティングテーブルは永続化しないのか)は、設定から毎回作り直せるので保存しなかった。**リースは作り直せない**。誰に何を貸したかは、そのときのやりとりでしか決まらないからである。

| もし保存しないと | 起きること |
|---|---|
| DHCP サーバーを再起動する | 貸し出し中の IP を「空き」だと思い込み、別の機器に配ってしまう → **IP の衝突** |

そのため、リースはファイルに保存する。

- **ACK を送る前に記録する。** 送った後に記録しようとして、その間にサーバーが落ちると、「貸したのに記録が無い」状態になる
- 起動したときに、ファイルからリースを読み込む

> 💡 dnsmasq は、`/var/lib/misc/dnsmasq.leases` というテキストファイルに、1 行 1 件で「期限・MAC・IP・ホスト名・クライアント ID」を書いている。自作するときの形の参考になる。

## 6. ネットワークまわりの実装方針

### ソケットの準備

| 手順 | 内容 | 理由 |
|---|---|---|
| ① UDP のソケットを作る | TCP ではなく UDP | 違い 1 |
| ② ブロードキャストで送れるようにする | ソケットの設定で許可する | 返事をブロードキャストで送るため |
| ③ LAN 側の NIC に限定する | ens37 に縛る | WAN 側で答えないため（違い 3） |
| ④ `0.0.0.0` の 67 番で待ち受ける | 特定の IP ではなく、すべてのアドレス | ブロードキャストを受け取るため（違い 2） |
| ⑤ 権限を落とす | 準備が終わったら root をやめる | 違い 4 |

### どこへ返すか（RFC 2131 の決まり）

| 届いたメッセージの状態 | 返す先 |
|---|---|
| `giaddr` が入っている（リレー経由） | **リレー**の 67 番へ |
| `ciaddr` が入っている（もう IP を持っている。延長など） | その **IP へ直接** |
| `ciaddr` が `0.0.0.0` で、ブロードキャストの印がある | **ブロードキャスト** |
| `ciaddr` が `0.0.0.0` で、ブロードキャストの印が無い | 配る IP ＋ 相手の MAC へ直接（できなければブロードキャストでよい） |
| NAK を返すとき（リレーなし） | いつも**ブロードキャスト** |

最初の実装は、「延長のときは IP へ直接、それ以外はブロードキャスト」で動く。

### 自分のアドレス（オプション 54）

要求が届いた NIC の IP（ens37 なら `10.0.0.1`）を入れる。クライアントは、この値で「どのサーバーの OFFER を選んだか」を伝えてくる。

### ファイアウォールとの関係

labs/05 でファイアウォールを作ったら、**LAN 側から UDP 67 番への通信を許可する**必要がある。許可し忘れると、DHCP サーバーは動いているのに、要求が届かない。

## 7. 自作ルーターの中での位置づけ

DHCP サーバーは独立したプログラムだが、ほかの機能とつながる点がある。

| つながる相手 | つながり方 |
|---|---|
| インターフェースの設定 | ens37 が `10.0.0.1/24` なら、配る範囲は `10.0.0.0/24` の中、ゲートウェイは `10.0.0.1`。**インターフェースの設定から DHCP の設定が決まる** |
| DNS（labs/07） | Router VM が DNS も担当するなら、配る DNS サーバーは `10.0.0.1`。dnsmasq は、DHCP で受け取ったホスト名を DNS に自動で登録してくれる（「`client.lan` で引ける」など） |
| ファイアウォール（labs/05） | LAN 側の UDP 67 番を許可する |
| 監視 | リースは「今つながっている機器の一覧」でもある。routerd の Traffic Monitoring で使える |

**routerd に含めるか、別のプログラムにするか**は、今後の設計判断になる（ADR の候補）。

| | routerd に含める | 別のプログラムにする |
|---|---|---|
| 長所 | 設定を共有しやすい（インターフェースが変わったら DHCP も追従、など） | DHCP が落ちてもルーター全体は止まらない。権限を分けられる。dnsmasq などの既存ソフトと入れ替えられる |
| 短所 | DHCP の不具合でルーター全体が止まるおそれ。権限が大きくなる | 設定の受け渡しの仕組みが要る |

## 8. 作る順番（実装方針）

いきなり全部作らず、**観察 → 受け取るだけ → 1 つ返す → 管理する**の順に進める。

| 段階 | やること | 確かめ方 |
|---|---|---|
| **0. 観察する** | labs/06 で、既存の DHCP サーバー（dnsmasq など）を Router VM の ens37 で動かす。Client VM を DHCP に戻し、DORA を `tcpdump -vv` で見る | Router VM で `sudo tcpdump -i ens37 -n -vv port 67 or port 68`。Client VM で `sudo dhcpcd -U ens33` に `dhcp_server_identifier=10.0.0.1` が出る |
| **1. 受け取って表示するだけ** | 67 番で受け取り、固定部分とオプションを読み解いて表示する。まだ返事はしない | 表示した `xid`・`chaddr`・オプションが、`tcpdump -vv` の表示と一致する |
| **2. 決まった 1 つの IP を返す** | DISCOVER に OFFER、REQUEST に ACK を、ブロードキャストで返す。配る IP は固定 | Client VM に IP が付き、`ping 10.0.0.1` が通る |
| **3. プールとリースを作る（メモリ上）** | 範囲から空きを選ぶ。同じ機器には同じ IP を返す。RELEASE で空きに戻す | 2 台目のクライアントに別の IP が配られる |
| **4. 永続化と延長** | リースをファイルに保存・読み込みする。延長（RENEWING / REBINDING）と NAK を扱う | サーバーを再起動しても、同じ IP が 2 台に配られない。15 分ごとの延長が `tcpdump` で見える |
| **5. 丈夫にする** | DECLINE、配る前の `ping`、仮押さえの期限切れ、壊れたメッセージ（長さが足りないなど）の無視、ログ | わざと変なメッセージを送っても落ちない |
| **6. 発展** | 直接返す方式、DHCP リレー（`giaddr`）、複数の LAN、IPv6（DHCPv6 は別のプロトコル。labs/08） | — |

### 試すときの注意

- **Client VM の IP が変わると、SSH の設定（`10.0.0.10`）が使えなくなる。** 段階 0 では、Client VM の MAC（`00:0c:29:20:6c:ff`。[labs/01 の `ip neigh`](../../labs/01-network-interface/README.md#5-近隣テーブルの観察router-vm--client-vm)）に `10.0.0.10` を**予約**しておくと、SSH の設定を変えずに済む。うまくいかなかったときに備えて、VMware のコンソールから操作できるようにしておく
- **既存の DHCP サーバーと自作のものを同時に動かさない。** 同じ 67 番を取り合ううえに、1 つのネットワークに DHCP サーバーが 2 台いる状態になる（[質問11](2026-10-11-dhcp-role-and-placement.md#質問11理解の確認とdhcp-サーバーの台数)）

> 💡 クライアントを何台も用意するのは大変である。Linux の「ネットワーク名前空間」（`ip netns`）と仮想の LAN ケーブル（`veth`）を使うと、Router VM の中に、仮想のクライアントを何台も作って試せる。

## まとめ

- DHCP サーバーも Web サーバーと同じく、**ソケットを作ってポートで待ち受けるプログラム**。ただし **UDP（67 番）** で、接続は作らず、1 通ずつ受け取って返す。
- Web サーバーとの最大の違いは、**相手がまだ IP を持っていない**こと。そのため、ブロードキャストで受け取り、MAC（`chaddr`）で相手を見分け、返事も工夫して送る（最初はブロードキャストで十分）。
- プロトコルは **ARP ではなく DHCP**（UDP の上の独自プロトコル）。ARP は、配る前・使う前の重複チェックなど、**まわりで使われる別の仕組み**。
- メッセージは「固定部分 ＋ オプション（番号・長さ・値の並び）」。`dhcpcd -U` で見た項目は、このオプションから来ている。
- サーバーの中心は、**プールとリースの管理**。リースは作り直せないので、**ACK を送る前にファイルへ保存する**。
- 作るときは、**観察 → 受け取るだけ → 1 つ返す → プールとリース → 永続化 → 丈夫にする**の順に進める。
